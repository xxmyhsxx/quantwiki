# Marlin：批处理 W4A16 GEMM 内核

权重量化的加速通常以「生成阶段受权重读取带宽限制」为前提。当同时生成多个序列时，计算强度上升，这个前提会变弱：既有 W4A16 内核在 batch 稍大时收益迅速消失。Marlin 研究的是这条边界能不能后移——在不放弃 4 bit 权重的前提下，让中等批量仍然接近内存带宽上限。

本页依据 MARLIN: Mixed-Precision Auto-Regressive Parallel Inference on Large Language Models（arXiv:2408.11743，下称论文，全文研读；抽取文本的 Kernel Design 段与精度表已回查作者 TeX 源码），并定向核对官方仓库固定快照 `1f25790bdd49fba53106164a24666dade68d7c90` 的 Python 接口与顶层 API。未运行任何内核，Ampere 之外的硬件行为不在本轮材料内。执行路径的共性分类见 [量化矩阵乘法的缩放与执行路径](quantized-matmul-scaling-execution.md)。

## 1. 问题与 roofline 判断

论文 §1 的出发点是：混合精度推理的既有实现在单 token（$M=1$）时接近理论加速，但批量增大后计算强度上升，收益不再明显。作者先做了量级估算（§3.1）：一个 A10 的 FLOPs/Bytes 约为 200，处理一个 token 每个权重需要 2 FLOPs，因此只要 batch 小于

$$b_{opt}\approx 50$$

内存读取就会主导运行时间；$b_{opt}$ 正是「延迟既不受内存限制也不受计算限制」的批大小，也是在最大吞吐下取得最低延迟的工作点。理论上把权重从 16 bit 压到 4 bit 可得 $16/4=4\times$，但每 $G$ 个权重还要存一个 fp16 尺度，$G=128$ 时额外 $16/128=0.125$ bit/weight，因此理想上限是

$$\frac{16}{4+0.125}\approx 3.87\times .$$

论文反复用这个 3.87 作为「理想线」，把测量结果与它对比，而不是与某个既有内核对比。这个习惯值得保留：加速比的参照系必须写明是理论上限还是某个实现。

## 2. 量化对象与数据布局约定

内核计算的是 $M\times K$ 的 fp16 激活矩阵 $A$ 与 $K\times N$ 的权重矩阵 $B$，其中 $B$ 对称量化为 INT4，尺度为「每列一个 fp16」或「每列中每 $G$ 个连续权重一个 fp16」，共 $K/G\times N$ 个尺度（论文 §3.4）。权重在推理期间静态，因此可以在离线阶段任意重排——这一条是后续所有布局优化的前提。

仓库接口与此一致（`marlin/__init__.py` 的 `mul`）：

```python
def mul(A, B, C, s, workspace, thread_k=-1, thread_n=-1, sms=-1, max_par=16):
    """Marlin FP16xINT4 multiply
    @A: (m, k) fp16
    @B: (k, n) int32 weight in Marlin format; see Layer.pack()
    @s: (k / groupsize, n) fp16 scales
    """
```

可见三件事：权重以打包后的 `int32` 传入，尺度形状按分组维度展开，`max_par` 控制「同时并行求解的 batch 64 问题数」。后两项分别对应第 5 节的批量重叠与分组尺度处理。

## 3. 为什么批处理会破坏原有的并行方案

论文 §3.3 列出四条困难，它们共同解释了为什么不能把单 token 内核简单放大：

1. 各层并行划分必须重新配置，确保瓶颈确实是压缩权重的读取，而不是反复重载高精度激活块 $A_{sm}$；
2. 既然运行时间由内存读取主导，读取路径必须打到峰值，而 $B$ 已被压缩，等于在更少字节上追求更高效率；
3. 中等 $M$ 时计算开销接近读取开销，需要极精细的重叠，还要额外处理量化元数据；
4. 第 1 条约束的划分方式，加上 $M$ 并不很大，压缩了并行选项，同时模型的实际矩阵形状对特定 GPU 未必友好。

## 4. 内存侧设计

**流量下界。** 一次矩阵乘需要触碰 $16MK+4KN+16MN$ bit（读两个操作数与写结果），执行 $MKN$ 次乘加。$M$ 小时算术强度低，$B$ 的读取应主导运行时间——但要让这一条在实现中成立，需要主动组织数据流。

**SM 级分块与 L2 流水。** 把输出切成长宽为 $M\times N_{sm}$ 的块，每个子问题交给一个 SM，$N_{sm}$ 取 64、128 或 256。取较大的 $N_{sm}$ 是为了减少 $A_{sm}$ 的重复读取，同时不能大到使 SM 数量不足。关键手段是利用 L2：GPU 可以同时从 L2 读入 L1、从全局内存读入 L2，于是论文给出「全局读仍是瓶颈」的条件（§3.4）：

$$\frac{2MK_{sm}+0.5K_{sm}N_{sm}}{B_{l2}}<\frac{0.5K_{sm}N_{sm}}{B_{gl}},$$

其中 $B_{l2}$、$B_{gl}$ 分别为 L2 与全局带宽，系数 0.5 来自 4 bit 权重（每权重半个字节）。$N_{sm}=256$ 时，即使 $M=64$ 仍保持受全局权重读取支配。

**最宽加载。** 目标是每线程 16 字节（128 bit）：这样一个 warp 用一条指令可加载 $32\times32=1024$ 个 INT4 权重。对 $A$ 块，这要求 $K_{sm}\ge 64$；对权重，因为静态可离线重排，作者把 $16\times64$ 的 tile 重排成连续内存，使加载与索引都变简单。为避免 $B$ 的一次性读取污染 L2、挤掉其他 SM 还要用的 $A$，加载使用 `cp.async` 并带 `evict_first` 提示。

**共享内存布局。** 权重由于离线预处理可连续拷贝进共享内存，不产生 bank conflict。激活侧则必须保证 $16\times16$ 的 fp16 块中，索引 $ij$、$(i+8)j$、$i(j+1)$、$(i+8)(j+1)$ 对应的 16 字节向量落在不同 bank，才能让 `ldmatrix.sync` 无冲突执行；做法是在共享内存中用 XOR 做索引变换。作者指出这同时保证 warp 读取连续子块时写入仍然连续。这些索引在寄存器中预计算并展开，因为主循环里动态计算太慢。

**流水与展开。** 全局到共享内存的加载用 `cp.async`，每次预取 $P-1$ 步之后要用的 $A_{sm}$、$B_{sm}$；流水深度取 $P=4$，理由是足以隐藏延迟、能在 $M=64$ 时放进共享内存，并且是偶数——保证 $P$ 次迭代后流水缓冲与寄存器缓冲下标同时回到 0，从而让共享内存寻址完全静态化。作者同时提到，这是让编译器正确重排指令、形成真正 double buffering 的最可靠方式。

**Warp 布局。** 若每个 warp 直接算 $M\times(N_{sm}/\#warps)$，在 $N_{sm}$ 较小时 tile 太窄，既不利于重排，也让张量核心出现顺序依赖。Marlin 改为主张：固定每个 warp 的子块宽度为 64，再沿 $K_{sm}$ 拆分，多个 warp 累加同一输出子块的部分结果，最后用对数归约合并。

## 5. 计算侧：INT4 到 FP16 的反量化

**位技巧。** 直接做类型转换很慢，作者沿用 Kim 等的二进制操作思路：把 INT16 中某个 4 bit 字段取出后，用一条 `lop3` 同时完成掩码与或操作，把它变成指数为 50、尾数低 4 位正好是目标值的 FP16，再减去一个常量（指数 50、尾数 0）即得无符号值；减去 8 得到有符号值，而 8 可以直接融进被减数的低 3 位。现代 GPU 能在一个 32 bit 寄存器里并行处理两个 16 bit 操作数，因此一次可反量化两个 INT4。

**寄存器内交错。** 反量化结果要直接进入张量核心所需的寄存器布局，所以权重离线重排使每个线程读到的 16 字节正好是它需要的 8 个权重的 4 个 $16\times16$ 块；在 INT32 内部，权重按 `64207531` 的顺序交错存放，以配合上述并行解码。

**累加方向。** 最内层执行 $M\times16$ 乘 $16\times64$ 的累加，按列推进，发 $16\times16$ 次 $16\times8$ 的 `mma.sync`。按列而不是按行，好处是可以把下一列 $B$ 的反量化与当前列的张量核心运算重叠。

**尺度与分组。** 逐输出通道量化时，尺度可以在写出前一次性乘到结果上。分组量化（对精度很关键）则必须在主循环内应用：作者把尺度按与权重相同的方式重排，使不同 $16\times16$ 块、同一类线程所需的尺度打包成一个 16 字节向量。按 $G=128$、$B_{sm}$ 为 $64\times256$ 计算，理论上每两个 tile 才需要加载一次新尺度；但实践发现编译器对主循环里的这种不规则性很敏感，导致 10%–20% 的整体变慢，因此改为每个子块都从共享内存重载尺度，用一点多余访存换取指令顺序稳定。

## 6. 分块：striped partitioning

前面几节在矩阵足够大、能沿 $N$ 轴均匀分到所有 SM 时才能接近峰值。实际形状往往不能整除，标准做法是再沿 $K$ 轴切分，但对许多常见层形状与 GPU 组合需要很多额外切分，并引入大量全局归约。

论文改用条带式划分：先算出每个 SM 应处理的 tile 数 $T=\#tiles/\#SMs$，从左上角开始按列分配；若到达当前列底部而该 SM 还没拿到 $T$ 个 tile，就继续从下一列顶部开始，因此条带可以横跨多列。这与 stream-k 划分思路相近，能在不增加太多归约的前提下让各 SM 负载大致均匀。同一 tile 列的条带之间按从下到上的顺序串行归约：最下方 SM 的结果最先就绪，最上方最后完成，顺序与完成时间一致。归约直接在输出缓冲区内以 FP16 进行，以提高 L2 命中并保持近似原地操作，只需一个小的锁缓冲同步。

另外，当 batch 不小于 64 时，可以「虚拟复制」$B$ 来计算条带索引，再用取模映射回原矩阵，并把 $A$ 指针推进到对应的 64 行输入段，从而在 prefill 这类大输入下显著减少全局归约。

## 7. 量化格式侧的配合

论文 §3.5 说明 Marlin 使用的格式与原始 GPTQ 略有不同，同时对 GPTQ 做了两处小改进：按组搜索最优裁剪阈值（思路类似 AWQ），以及支持可变长度的校准序列。作者称这两处带来小而一致的精度提升，并提供了与原格式互转的脚本。

论文用一张困惑度—大小曲线给出与未压缩模型的对照：在同等困惑度下模型约为原来的 $3.33\times$ 更小。作者同时指出这并非无损，理想值在同位宽与分组下是 $3.87\times$。也就是说，压缩收益与理想上限的差距有明确来源，不是含糊的「接近无损」。GPTQ 的补偿机制与格式本身见 [GPTQ](../methods/gptq.md)。

## 8. 2:4 稀疏扩展

Sparse-MARLIN 在 4 bit 权重之上叠加 NVIDIA Ampere 的结构化 2:4 稀疏。难点在于 `mma.sp` 要求稀疏矩阵作为左操作数，因此内核在内部把问题改写为 $(B^{\mathsf T}A^{\mathsf T})^{\mathsf T}$，即用 $N\times K$ 的权重乘 $K\times M$ 的激活、输出 $M\times N$；$B$ 可离线预处理，$A$ 的转置可用 `ldmatrix` 的 `.trans` 在共享内存中即时完成（§4）。

两种新结构：非零值按 $N\times K/2$ 表示，再套用密集 Marlin 的压缩方式，8 个 4 bit 值装进一个 32 bit，得到 $N/8\times K/2$ 的最终尺寸，且每个 $64\times16$ tile 重排后每线程可做 128 bit 的连续加载与转置写出；元数据保存原矩阵中非零元素的位置，2:4 下每个索引 2 bit，并按 `mma.sp` 的 sparsity selector 约束重新排列，使一条 `ldmatrix` 覆盖后续四次 `mma.sp` 所需信息。这些预处理都是离线一次完成。

## 9. 证据与解释边界

**内核层（论文的内核基准图与真实层形状图）。** 在 A10、$72\text{k}\times18\text{k}$ 的大矩阵、4 bit、$G=128$ 下：单 token 时 PyTorch、AWQ、ExLlamaV2、bitsandbytes 等内核都接近 $3.87\times$ 的理想线，但随输入数增加迅速退化；Marlin 在 batch 约 16–32 之前保持接近 $3.87\times$，之后随进入计算受限区间而下降，batch 128 时约 $1.5\times$。作者明确说明不同方法的尺度格式并非完全一致，因此这是量级比较而非严格同构比较。

真实层形状（batch 16）：RTX 3090 等消费级 GPU 收益更高，A100 更低，原因是后者的显存带宽与算力都更高，流水启动延迟或划分不优等开销在中小矩阵上相对更明显。锁频测试中，降低时钟显著损害其他内核的相对加速比，而 Marlin 相对低频基线仍接近最优。prefill 场景（大 batch）下，直到 batch 1024 都几乎与未压缩的计算受限矩阵乘持平，更大输入时约有 10% 变慢，作者将其留作后续工作。roofline 分析显示 batch 小于 64 时受内存限制、更大时受计算限制，与前面的估算一致；作者也记录了长时高负载下 GPU 自动降频、FLOP/s 随之下降的现象。

**端到端（论文表 1、表 2 与端到端生成及服务基准图）。** 与 vLLM 的 FP16 基线相比，Llama-2-7B 在 A10 上生成阶段最高约 $3\times$（Sparse-MARLIN 再叠加约 $1.2\times$）；在 RTX A6000 的服务基准中 TPOT 约 $2.8\times$、Sparse-MARLIN 约 $3.3\times$，且加速比随 QPS 上升而增大——作者的解释是 Marlin 降低了单请求延迟，使平均批大小低于 FP16，从而进一步提升相对收益。表 2 的多模型多卡结果显示所有场景都有改善，且在内存受限、GPU 较弱或数量较少时收益最大。

**精度（论文表 1）。** Llama-2-7B：MMLU 47.88→43.59（INT4）、WinoGrande 71.82→68.75、ARC-Challenge 51.19→48.55，均值 56.96→53.63；INT4 + 2:4 一列为 48.81/73.09/53.67，均值 58.52，**高于**原始模型，原因是该模型额外用合成数据做了知识蒸馏微调，作者也说明了这一点。因此这一列不能用来支持「稀疏量化提升精度」。

## 10. Strong / Weak 与方法关系

**Strong：**把「压缩收益在什么批量下仍然成立」变成可复核的 roofline 判断，并在实现层面给出了完整的重叠策略：离线重排换取 128 bit 加载、`cp.async` 与流水深度选择、针对编译器行为的尺度加载策略、条带划分减少归约。设计可迁移到其他量化格式，作者也给出 2:4 稀疏的扩展实例，说明该并行方案不只适用于一种位宽。

**Weak：**结论建立在 Ampere 级 GPU 的特定指令（`cp.async`、`ldmatrix`、`mma.sp`）与 128 bit 加载之上，论文没有给出 Hopper 及以后的测量；精度不是本文重点，只有 Llama-2-7B 一组表；格式与原始 GPTQ 不同，需要转换脚本；内核级结论绑定大矩阵与 $G=128$，小矩阵、其他分组与其他位宽需要重新验证。

它与相邻工作的关系可以这样区分：[GPTQ](../methods/gptq.md) 与 [AWQ](../methods/awq.md) 决定权重误差与表示，Marlin 决定这些权重在批量下如何被快速读取与计算；[执行路径页](quantized-matmul-scaling-execution.md) 说明存储、反量化与计算的一般分类，本页是其中「W4A16 压缩 + 即时反量化」路径的一个完整实现案例。部署侧把格式与内核打包成可用后端（vLLM 中有 gptq_marlin／awq_marlin 等方法名）的机制见 [部署框架与后端支持](quantized-llm-deployment-backends.md)。

## 11. 局限与未验证

- 未运行 Marlin 或其 vLLM 集成，未复现任何速度与精度数字；本页性能与精度均为作者报告。
- 内核实现只在 Python 接口与顶层 API 层面核对，`marlin_cuda_kernel.cu` 的指令级细节未逐行审查。
- 论文未给出 Hopper 及更新架构的测量；2:4 路径要求权重可离线重排，且与结构化稀疏工具链配合，本轮未验证其端到端可用性。
