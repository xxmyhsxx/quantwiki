# Wiki Prune

## 1. 任务与设计目标

**保留有效知识，减少冗余，改善知识组织和阅读路径。** 从段落和章节判断内容的作用，按需要压缩、合并、移动或删除页面。

核心判断是：这段内容承担什么解释责任？删减后，读者是否失去必要的理解、判断或使用能力？

剪枝完成后，原来需要回答的关键问题仍能回答，独特知识有明确的承接位置，重复阅读减少。字数和页面数只描述改动，不作为优化目标。

## 2. 使用边界

用于用户要求精简 Wiki、去除重复内容、合并碎片页面或整理重叠解释的任务。处理范围可以是一页、一个主题或全库，实际修改按用户授权执行。

`wiki-review` 负责判断内容质量，`wiki-prune` 负责完成内容取舍与组织上的精简。剪枝直接读取相关内容并判断，无需先执行完整 review。

首版以保留有效知识为前提。方法较旧、近期未使用、知识基础或篇幅较长，都不足以作为删除理由。整个研究方向是否退出 Wiki，属于知识库范围的选择，另行讨论。

## 3. 输入设计

需要目标 Wiki 入口与剪枝范围；可结合用户指出的重复、过碎或冗长问题。读取目标的组织规范及实际正文，按需要查看关联页面、引用和来源。

## 4. 原则设计

- **按解释作用取舍。** 确认内容是否增加定义、机制、推导、条件、证据、例子或反例；措辞相近不等于知识相同。
- **保留独特知识。** 合并和移动时保留独有信息、适用条件及来源，依据页面职责与内容质量选择主要解释位置。
- **兼顾集中维护与局部可读。** 公共机制集中解释，各页保留理解当前问题所需的概述与联系，避免用链接替代核心解释。

## 5. 工作流程设计

### 1. 明确解释职责

读取指定范围及必要的关联内容，弄清页面和主要章节分别回答什么问题。用这些问题作为剪枝后的阅读检查依据。

页面、段落和链接是否有价值，需要结合正文判断；检索和相似内容匹配只用于定位候选。

### 2. 判断与取舍

| 内容情况 | 处理方式 |
| --- | --- |
| 反复表达相同结论，没有新增解释 | 删除或合并重复表述 |
| 多页重复完整的公共机制 | 选择主要解释位置，其他页面保留必要概述及与当前问题的联系 |
| 页面没有独立解释职责，但含有独特内容 | 将独特内容并入合适页面，再处理旧页 |
| 泛化提醒、空泛评价或无信息增量的总结 | 删除 |
| 内容有效，但偏离本页问题 | 移到更合适的位置 |
| 相似表述实际采用不同条件、版本或证据 | 保留差异，必要时集中对照 |
| 结论有事实或证据疑点 | 定向核查后修正，未解决的疑点如实保留 |

取舍要能说明删减理由，以及独特内容在哪里承接。没有合适承接位置时保留原内容。短概述、具体应用、例子和反例是否保留，取决于它们对当前阅读的作用。

### 3. 执行剪枝

按上述判断精简正文、合并或移动内容。调整页面结构时保持核心解释连贯，并同步受影响的链接、章节锚点、来源、资源和导航；按目标 Wiki 的约定记录实际变动。

### 4. 沿阅读路径复核

从实际入口重新阅读，检查关键问题能否回答、推理是否连贯、必要条件和证据是否仍在、独特内容是否确实完成承接。改成链接的内容，还要检查目标是否提供所需解释，以及阅读是否产生不必要的往返。

完成与改动范围相称的格式、链接和来源路径检查。机械检查用于验证结构，正文阅读用于判断知识是否保留完整。

## 6. 输出设计

主要交付是剪枝后的 Wiki。简要说明处理范围、重要删减与合并的理由、独特内容的承接位置、实际检查和遗留问题。只分析时交付具体建议，不修改文件。

## 7. 校验设计

执行结果主要检查三点：关键解释是否保留，重复是否减少，阅读路径是否更清楚。

设计与实现核对可使用以下场景：

| 场景 | 应有的处理 |
| --- | --- |
| 两页重复公共定义，但分别包含不同应用条件 | 集中公共解释，保留各自条件与联系 |
| 页面很长，但包含必要推导和反例 | 保留其解释作用，只处理真实冗余 |
| 碎片页的独有知识适合并入主页面 | 先完成内容与来源承接，再同步旧入口 |
| 段落疑似重复，实际讨论不同版本或假设 | 明确差异，不直接删掉其中一项 |

这些场景用于检查 Skill 设计；实际剪枝仍以当前内容和阅读结果为依据。
