# 量化 Wiki 能力包

## 1. 任务与设计目标

通过一个入口，让应用项目使用量化 Wiki 的知识、研究方法和算子开发流程。知识正文留在原 Wiki，应用代码、环境和运行记录留在应用项目。

## 2. 使用边界

入口按需读取内部规范。知识修订和论文入库由 Wiki 维护端处理，这些维护能力不随包下发。内部能力提供反馈材料，由入口统一回传。

## 3. 输入设计

当前应用任务、目标、约束和工作目录；Wiki、源包及反馈位置由 `package.json` 绑定。

## 4. 原则设计

入口、内部 Skill 和辅助材料共用一个发布版本，避免只安装入口却缺少执行方法。`package.json` 记录三项能力、全部文件及校验值，并绑定 Wiki、源包和反馈目录的绝对路径；应用目录不会被误当作知识库。

每次任务用 `prepare` 建立一份完整快照，执行期间始终读取这份快照。其他任务更新安装目录，不会改变当前任务的规范。知识正文不复制到包里，也不随这份快照冻结；正文更新无需升级包，包内文件变化则需要重新发布。

工具保护已有定制、拒绝来源冲突，更新时保留旧包备份。源端不可达或尚未发布时，可继续使用经核验的有效本地包，并说明无法确认最新。更新须有授权，不能为消除差异覆盖使用方修改。

## 5. 工作流程设计

| 能力 | 用途 | 执行规范 |
| --- | --- | --- |
| wiki-query | 定位、解释、比较和分析已有知识 | [查询](skills/wiki-query/SKILL.md) |
| wiki-research | 查证、推导或验证应用问题 | [研究](skills/wiki-research/SKILL.md) |
| wiki-kernel-writing | 实现或优化 CUDA/Triton 算子 | [算子编写](skills/wiki-kernel-writing/SKILL.md) |

正常流程为：**prepare 准备版本 → 使用所需能力 → feedback 回传一次反馈**。具体命令和字段见 [入口规范](SKILL.md)。

准备、安装和反馈的完整性检查由工具完成，成功后直接继续；失败或结果矛盾时再排查。任务续接复用已有快照，不重复准备或反馈。

查询通过 wiki-query 的主题 references 和定向搜索进入正文，已知页面直接读取，不预读整份 INDEX、SELF、READING 或 LOG。references 提供选路线索，结论来自正文。原始材料只在研究需要查证时按范围读取。

算子开发在应用环境执行。入口可在准备阶段整理知识；进入算子迭代后使用已准备材料和项目工具，不再查询外部 Wiki。

用户明确要求接入时，向可访问的项目目录或已确认的共享 Skill 目录安装完整包。工具创建缺少的目录；相同内容可复用，已授权的干净旧版本可更新。仓库 URL 或服务器地址须先对应到实际接收目录，不猜测路径。

发布维护在源包进行：同步设计与执行，验证文件与依赖，再用递增版本生成清单。首次发布需要绑定和能力元数据；后续沿用已有清单。发布不会自动安装到真实项目或推送 Git。

## 6. 输出设计

反馈保留任务、已读位置、结果、限制及有依据的改进建议；实验结论附版本、配置和证据位置。反馈仅新增记录，不直接修改公共知识或源 Skill。写入失败时交付反馈文本；纯安装不生成知识使用反馈。

安装完成、知识可访问和应用实际运行是不同结果，交付时只说明已验证的部分。

## 8. 校验设计

工具仅依赖 Python 标准库。维护测试为 `scripts/test_package.py`，在临时目录验证：完整安装与重复使用、授权更新、定制和冲突保护、失败回退、任务快照固定、反馈写入。涉及随包材料时，另检查临时安装和快照是否完整；查询效果用实际正文阅读核对。测试结果不代表模型或 GPU 已运行。

## 9. 文件结构

包包含入口 `README.md`、`SKILL.md`、`package.json`，工具 `scripts/package.py` 及其测试，以及三项内部能力的 README 和 SKILL。wiki-query 另有五份主题 references。包内引用使用相对路径，Wiki 引用使用绑定绝对路径，整个目录一起安装和建立快照。
