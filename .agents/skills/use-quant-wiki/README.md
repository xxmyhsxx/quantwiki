# 量化 Wiki 能力包

状态：入口、三个包内 Skill 和发布安装工具已实现。实际发布版本、绑定与完整载荷以 `package.json` 为准；外部真实项目接入和模型部署按指定目标另行验收。

## 1. 任务与设计目标

量化 Wiki 面向应用项目发布一个完整能力包。包以 `use-quant-wiki` 为统一入口，内部包含知识使用、实际问题研究和算子编写能力。应用接入整个包，由入口根据当前任务选择并读取内部 Skill。

入口还承接外派请求：用户提供外部项目地址并要求接入时，发布端实际创建目标 Skill 目录、复制完整包并核验安装。只给操作说明、只创建空目录或只复制外层入口，都不能称为完成外派。

知识正文继续保留在原 Wiki。应用 AI 直接读取相关知识，将其用于方案、实现和诊断；执行 Skill 使用应用自己的代码、环境和结果目录。使用中形成的疑点和通用认识通过反馈交给 Wiki 维护端。

| 关键问题 | 采用的方法 | 完成依据 |
| --- | --- | --- |
| 应用需要分别配置多个 Wiki Skill | 提供一个入口，随包带入内部能力清单和完整执行材料。 | 入口能在应用目录中按需读取正确的内部规范。 |
| 用户给出外部项目地址后仍需手动接入 | 解析目标工作区，创建目标目录并安装完整包。 | 指定项目中的包实际存在，文件、版本和绑定核对通过。 |
| 从应用目录查询时读错 Wiki | 在包中绑定知识库、源包和反馈目录的绝对位置。 | 实际阅读位置属于指定 Wiki，应用目录不被当作 Wiki。 |
| 外派后执行方法落后或内容被修改 | 统一包版本，核对发布清单和安装内容。 | 能区分最新镜像、旧镜像、项目定制内容和未发布修改。 |
| 源端更新改变正在进行的实验 | 任务开始前检查更新，执行过程中固定所用包版本。 | 结果能对应本次实际使用的指令、实现和验证条件。 |
| 应用任务与知识维护混在一起 | 应用保存代码与运行记录，入口只向 Wiki 新增使用反馈。 | 查询不改知识，应用结果与可复用认识的落点清楚。 |

包是对外交付和版本核对的单位。内部 Skill 保留各自职责，不分别建立外派版本。知识页面更新不使包升级；入口、内部指令或随包材料变化后，重新验证并发布整个包。

## 2. 使用边界

本包用于需要量化、模型推理、部署、GPU 执行或评测知识支持的应用任务。用户明确要求使用量化 Wiki，或当前任务匹配本包的能力时，入口判断需要哪些知识和方法，不要求用户逐个指定内部 Skill。

用户提供外部项目地址并明确要求外派、安装或接入时，入口进入外派安装流程。外派的是本能力包，知识正文仍在绑定的原 Wiki；单纯查询知识不触发外部目录创建或安装。

首版内部能力如下，完整执行材料在包内统一维护：

| 内部能力 | 包内材料 | 包内职责 |
| --- | --- | --- |
| `wiki-query` | [设计](skills/wiki-query/README.md)、[执行规范](skills/wiki-query/SKILL.md) | 直接阅读知识，完成定位、解释、比较或分析，提供依据和使用反馈所需信息。 |
| `wiki-research` | [设计](skills/wiki-research/README.md)、[执行规范](skills/wiki-research/SKILL.md) | 用知识研究应用中的实际问题，按任务要求形成方案、实施验证和整合结果。 |
| `wiki-kernel-writing` | [设计](skills/wiki-kernel-writing/README.md)、[执行规范](skills/wiki-kernel-writing/SKILL.md) | 在应用环境中实现或优化算子，完成编译、正确性检查、性能测量和交付。 |

`wiki-ingest`、`wiki-review`、`wiki-prune` 和 `skill-creator` 继续承担 Wiki 维护，不随首版能力包下发。研究发现需要论文入库、修改知识或调整共享方法时，交付依据和建议，由维护任务处理；不能假定应用镜像中有这些维护 Skill。

知识使用能力读取根目录的 `SELF.md` 与 `wiki/` 内的导航、规范和正文，适配本项目实际入口。单纯使用已有知识时不读取 `raw/`。研究需要核验来源或读取其他材料时，由当前研究任务明确范围，区分知识页、来源核查和实际实验。

源码维护位置为本仓库。上述三项能力已完整迁入包内，原兄弟目录不保留另一份独立维护副本；项目任务通过统一入口选择包内规范。

当前工作仅在量化仓库内完成源包建设。不修改通用模板，不安装到用户共享目录或真实应用项目，不连接服务器。外派功能纳入本包设计；实际外派在用户提供目标并明确要求接入后开展。

## 3. 输入设计

入口从当前任务和应用上下文取得目标、约束、已有观察、需要的输出及应用工作区。信息已经明确时直接使用，不要求填写固定表单。研究与算子开发所需的对象、环境和验证条件，由对应内部 Skill 取得。

外派输入为目标项目地址及本次安装要求。能解析为当前工具可读写的工作区时，取得其实际绝对路径；默认安装到 `<项目根目录>/.agents/skills/use-quant-wiki/`。本机目录直接使用；仓库 URL 或服务器地址缺少可访问的接收工作区时，先取得本次所需的接收路径或连接信息，不把 URL 当作本机目录。

本包的知识库绑定为 `/Users/xiao/Desktop/量化`，源包位置为其 `.agents/skills/use-quant-wiki/`，反馈位置为其 `query-feedback/`。镜像中的绑定保持一致。路径不可访问时报告具体限制，不根据应用当前目录猜测知识库，也不自动改成另一位置。

应用的 GPU、模型、依赖和服务器位置由应用任务确定，不沿用本 Wiki 的历史实验环境作为默认执行目标。

## 4. 原则设计

1. **一个入口，按需使用内部能力。** 入口保存用途、选择条件和包内路径；完整方法保留在内部 Skill，不在入口重复编写。内部规范通过明确路径读取，不依赖平台将嵌套目录识别为独立 Skill。
2. **直接使用原 Wiki。** 根据当前问题读取知识正文和必要关联，知识依据实际阅读内容，不以标题命中、链接存在或模型记忆替代。
3. **完整镜像与单一源维护。** 发布和安装以整个包为单位；只同步包清单内的材料，保留应用其他 Skill 和已有修改。
4. **发布版本与工作中的修改分开。** 只有版本、清单和内容校验一致的已发布源包可供更新。源文件正在修改或尚未发布时，不把它复制为最新镜像。
5. **任务使用固定版本。** 开始任务前核对更新，执行过程不替换已使用的规范。新的任务再检查源版本。
6. **结果匹配证据和落点。** 应用代码与运行记录归应用，知识修订归 Wiki 维护端。反馈中的推测、来源陈述和实际验证分别说明。

## 5. 工作流程设计

### 5.1 发布源包

维护者完成入口、内部 Skill 和实际需要的随包材料，核对规范一致、包内引用和运行依赖。三个内部 Skill 没有独立的 `references/` 或 `scripts/`，首版不创建无用途的占位材料。

包清单记录名称、一个递增的发布版本、绝对绑定、内部能力的用途和路径、完整文件清单及内容校验值。清单本身不纳入自己的内容摘要；应用的安装记录也不属于源包载荷。改变发布材料后更新包版本并重新校验，知识正文不纳入包清单或摘要。

使用一个 Python 标准库辅助工具完成发布清单生成、状态核对、首次安装和完整镜像同步；不引入独立服务、依赖管理平台或中央应用登记。完成必要验证后发布；没有形成有效清单的内容属于未发布修改。

### 5.2 向指定项目外派并创建

1. **确认接收位置。** 将用户给出的地址解析为可访问的项目工作区，读取该项目已有的协作约定，明确包的最终安装路径。已给出清楚的目标和外派要求时，直接执行该范围内的创建与复制，不重复询问相同授权。
2. **核对源包。** 使用绑定位置的有效已发布包，核对版本、完整清单和内容。源包尚未实现、未发布或校验不一致时，交代具体缺项，不能用空目录或不完整文件冒充已完成安装。
3. **创建目标目录。** 根据明确的接收路径创建缺少的项目目录、`.agents/skills/` 和能力包目录。保留项目已有代码、配置和其他 Skill；不因安装包而初始化 Git 或改写项目说明。
4. **复制完整包。** 复制入口、包清单、内部 Skill 和实际随包材料，保持知识库与反馈绑定。同名且完整内容一致时复用；同名旧镜像按第 5.3 节处理；同名内容属于其他来源或已经被项目修改时，保留原内容并说明冲突，不直接覆盖。
5. **核验并交付。** 重新读取目标中的入口、清单和内部规范，核对目录实际存在、文件齐全、版本及内容一致、包内路径能解析。记录该项目的安装来源、版本和内容标识，交付项目根目录、安装路径及核验结果。

目标环境能访问绑定 Wiki 时，核对知识入口可读；不能访问时，分别报告包文件已经复制和知识连接尚未可用，不能宣称应用已能使用 Wiki。权限、连接或工具阻塞时报告具体位置、已经完成的部分和未完成项。

本流程必须有实际目录、完整文件和核验结果。列出命令、完成设计或发出复制请求都不构成外派成功。用户另行指定接收目标前，只实现和验证本仓库的外派能力，不向其他真实项目安装。

### 5.3 核对镜像与更新

入口开始任务时，只核对当前安装包与绑定源包。应用保存自己的安装版本和内容标识；Wiki 登记源包当前发布版本，不追踪每个外派副本的位置。

| 核对结果 | 行动 |
| --- | --- |
| 版本与完整内容一致 | 直接使用已安装包。 |
| 本地仍是原安装内容，源端有新的有效发布版本 | 在本次接入约定允许更新时，同步完整包，核对内容，再重新读取新入口和所需内部规范。 |
| 本地内容已经被项目修改 | 保留改动，说明差异；作为项目定制版处理，不直接覆盖。 |
| 源端内容与发布清单不一致 | 说明源端尚未形成有效发布，不复制工作中的修改。 |
| 源端不可访问 | 使用已有可用的安装版本，并说明本次未确认最新状态。 |
| 当前任务已经开始执行 | 固定本次版本，新任务再检查更新。 |

同步只更新该能力包。先准备完整的新包并核对，再替换目标；不能留下只更新入口、内部方法仍是旧版的混合状态。更新动作不修改 Wiki 知识，也不修改应用代码、测试或实验记录。

开始执行时保存所选版本的完整包快照，后续规范和随包材料均从该快照读取。其他调用更新安装镜像时，不修改正在使用的快照。任务记录保留包版本、内容标识和快照位置；这份快照不产生另一套发布版本。

### 5.4 选择能力并完成任务

入口根据问题选择内部规范。只需知识时使用 `wiki-query`；需要研究路线、解释现象或验证判断时使用 `wiki-research`；明确的算子实现与优化交给 `wiki-kernel-writing`。同一任务需要多项能力时，按实际依赖顺序组合，不默认加载全部内容。

知识使用先明确目标 Wiki，读取 SELF、INDEX、相关正文和必要关联，再结合应用条件形成结果。包内 `wiki-query` 支持定位、解释、比较与分析，保留实际阅读依据。

研究过程可复用包内知识使用和算子能力。需要资料入库、知识修订或方法改进时向维护端提交反馈，不把未下发的兄弟目录当成可用依赖。

算子开发使用应用的 Reference、代码、测试、环境和实验记录。保留现有编译、正确性、Benchmark 和最终验证要求。Wiki 支撑任务准备与方法改进，入口不在算子迭代循环中插入外部 Wiki 查询；执行阶段继续遵守随包材料与应用环境的运行约定。

### 5.5 回传使用反馈

每次知识使用、研究或执行调用完成后，在绑定的 `query-feedback/` 中新建一份唯一反馈。入口整合各内部能力的反馈，不为同一次调用重复写多份日志，不追加或覆盖已有日志。仅外派安装时交付安装记录，不制造知识使用反馈。

反馈记录包版本、任务摘要、实际使用的内部能力、已读知识位置、结果摘要、限制和有依据的改进建议。引用应用实验时保留实际代码版本、配置与证据位置，不将未验证的效果写成知识结论，不复制完整业务代码或对话。

没有发现知识缺口或方法问题时如实说明。反馈目录不可写时交付反馈文本并说明未回传，不改写其他位置。反馈不自动修改正文、导航、SELF、源 Skill 或包版本。

## 6. 输出设计

主要交付是当前应用问题的答案、方案、实现或经过验证的进展。说明 Wiki 知识的作用、实际使用的包版本和内部能力、证据范围及剩余未知。应用执行结果遵守对应内部 Skill 的交付要求。

外派请求的交付是指定项目中实际创建的完整能力包、安装记录及核验结果。区分文件已安装、绑定知识可访问和实际能力已运行验证，不以操作说明代替目标中的产物。

分别报告设计完成、源包可执行、已发布、镜像安装和实际使用的状态。版本标识或文件复制成功不能代替实际使用验证。

## 8. 校验设计

设计和静态核对不代替工具运行与实际应用验证。

在本仓库内使用临时镜像检验以下行为，不写其他真实项目或用户共享目录：

- 从应用式工作目录进入，入口仍指向原 Wiki，并读取正确内部规范。
- 给出新的接收路径后，缺少的项目和 Skill 目录实际创建，完整包安装和核验通过；同内容重复外派不改动既有包。
- 目标只有仓库 URL、接收位置不可访问、同名来源冲突或安装受限时，准确交付缺项及实际完成范围，不伪报外派或知识连接成功。
- 知识使用给出来自实际正文的结果；Wiki 正文变化不会使包版本改变。
- 首次安装、同版本复用及干净旧镜像更新后，完整文件清单与内容相符。
- 本地修改、源包未发布和源端不可访问分别处理，原有文件得到保留。
- 同一镜像被另一调用更新后，已有任务仍读取自己的完整版本快照。
- 包内研究不调用未下发的维护 Skill；算子执行遵守当前应用环境和固定版本。
- 一次调用只新增一份反馈，写入失败如实报告，知识和源规范没有被顺带修改。

静态检查、场景推演、工具实际运行和应用或 GPU 实测分别报告。外部安装与模型部署仍需指定实际目标后另行验收。

## 9. 文件结构

包的实际结构如下：

```text
use-quant-wiki/
├── README.md
├── SKILL.md                    统一入口与内部能力选择
├── package.json                统一包版本、绑定与发布清单
├── scripts/
│   ├── package.py              发布、核对、安装、快照与反馈
│   └── test_package.py         包生命周期与保护边界验证
└── skills/
    ├── wiki-query/
    │   ├── README.md
    │   └── SKILL.md
    ├── wiki-research/
    │   ├── README.md
    │   └── SKILL.md
    └── wiki-kernel-writing/
        ├── README.md
        └── SKILL.md
```

包内相对引用、项目介绍和 Agent 入口随目录结构同步。知识使用操作以绑定 Wiki 根目录解析路径，应用执行以应用工作区解析代码和结果路径。指向 Wiki 与未随包内容的文档入口采用绑定绝对位置，避免镜像里的相对链接指向应用目录。镜像与源包使用同一结构，不保留依赖原兄弟目录的执行引用。

工具使用 Python 标准库，运行时无需安装依赖。将 `quantwiki_package` 设置为本次使用的包目录绝对路径；命令返回 JSON，核验失败或冲突会返回非零退出状态：

```sh
python3 -B "$quantwiki_package/scripts/package.py" --package "$quantwiki_package" verify
python3 -B "$quantwiki_package/scripts/package.py" --package "$quantwiki_package" status
```

用户给出本机目标并要求外派时，将 `quantwiki_project` 设置为该项目绝对路径，执行 `install --project "$quantwiki_project"`；明确授权同步干净旧镜像时加 `--allow-update`。`snapshot --output` 创建不存在的完整任务快照，`feedback --input` 读取当前任务反馈 JSON 并唯一新建回传记录；具体执行顺序和交付要求见 [入口规范](SKILL.md)。

维护者修改源包载荷并完成验证后，在源目录执行 `publish --version`，使用大于现有发布版本的正整数。首次发布用 `--metadata` 指定含 `schema_version: 1`、名称、绑定和内部能力的 JSON；后续沿用已有清单中的元数据。发布生成完整清单，不自动向任何项目安装或推送 Git。包内测试可运行 `python3 -B "$quantwiki_package/scripts/test_package.py"`，临时项目和绑定均位于当前仓库内并在结束后清理。
