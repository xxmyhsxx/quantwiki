# 算子编写

## 任务

适用于从高层实现编写 GPU 算子，或优化已有算子的融合、布局和执行策略。概念解释、代码阅读、静态评审及纯框架层优化不自动进入此流程。

## 输入

读取任务、参考实现、调用入口、测试、构建配置及已有实验，明确：

| 条件 | 要确认什么 |
| --- | --- |
| 算子语义 | 数学计算、输入输出、广播、归约、动态维度、数值要求和集成方式 |
| 目标环境 | GPU、CUDA/Triton 等实现方式、编译与运行入口 |
| 必须支持的输入 | shape、dtype、layout 和重要边界条件 |
| 正确性 | 可信参考实现、测试范围、容差及其他数值约定 |
| 性能 | 比较基线、主指标、目标（如有）、正式测速协议和多个输入的整体比较方法 |
| 预算 | 已约定的候选版本数、Profiling 次数、GPU 时间或其他限制 |

## 原则

规范来自入口固定的包快照，代码、环境和实验记录留在应用项目。当前没有随附 references 或脚本；使用任务材料、项目代码文档和实际可用工具。入口可提前通过 query 或 research 准备知识，进入算子迭代后不再查询外部 Wiki。额外知识需求交反馈或后续研究。

## 工作步骤

### 1. 确认语义与评测条件

复用已有配置和记录。必要信息未知时先从材料和环境核实，不能猜硬件、输入范围、容差、基线或预算。无法补齐时说明阻塞哪一步，继续不依赖它的工作。

参考实现定义应当算出什么，不要求复制其执行结构；基线用于性能比较，两者可以不同。确认正式评测入口，不另选更有利的比较对象。目标、正确性和评测条件明确后再进入依赖它们的实现与测量。

### 2. 建立基线与首版实现

按第 3 步的方法验证基线正确性并测量全部必需输入；记录实现、环境、协议和结果。无效基线先修复，不能带入性能比较。

首版选简单、可验证的实现；后续版本执行第 5 步形成的假设。每版保留可恢复代码、版本标识、改动和设计说明，代码变化后重新验证。

基线也满足交付约束时可作为初始最佳实现，否则最佳实现暂时为空。最新尝试与最佳实现分开保存，失败和回退不覆盖已有成果。

### 3. 编译、检查正确性、测速

每个版本依次通过以下检查；某阶段失败时保留错误与未执行阶段，不跳到后续测量：

1. **编译。** 使用已确认的构建入口，保存结果和错误。失败则修复后重编译；只修编译且主要假设不变时可沿用版本标识，但保留修复记录。结构或假设明显变化时另建可区分版本。
2. **正确性。** 与可信参考实现比较，覆盖全部必需输入，并按算子特点检查代表性、边界、不规则形状、随机输入、重要数值范围及支持的数据类型。记录通过/失败、检查范围、适用的绝对与相对误差和失败输入。失败优先修复，再从编译开始；不放宽容差换取通过。
3. **测速。** 只测正确性通过的版本。按正式协议完成 warmup、重复运行、必要同步和统计汇总，测量全部必需输入。记录延迟或吞吐、基线比较、加速比、重复次数及执行入口。

比较时固定 GPU、shape、dtype、layout、容差、warmup、次数、计时方法、统计量、基线和指标。任务要求改变条件时记录变化，重建可比数据，不混用旧结果。优先采用协议约定的稳健统计量，如中位数。

满足全部任务约束且统一协议下目标指标更优时，才替换最佳实现。首次合格版本可登记为当前最佳，但不意味着超过基线。差异接近噪声时在预算内复测，不能确认改善则保留原最佳。回退保留结果；无效或不可比的测量先修复，不能用来下性能结论。

### 4. 按需要分析性能瓶颈

以下情况应做针对性 Profiling：首个正确版本明显低于目标；连续两个有效版本未改善最佳结果；出现无法解释的回退；瓶颈不清或有多个竞争解释。编译、正确性或测速结果已足够定位时，直接进入第 5 步。

按问题选指标，例如执行时间、SM 利用率、内存吞吐、缓存行为、占用率、寄存器/共享内存用量、warp 停顿、Tensor Core 利用率和启动配置。使用实际可用的工具，保存对应版本、输入、命令和原始输出，上下文只保留相关摘要。指标本身不直接决定改什么代码。

工具、依赖或预算不足时记录限制。剩余证据足以形成可验证假设才继续，否则按停止条件处理。

### 5. 决定下一次改动

根据测量和实验历史写清：观测问题与证据、可能原因和未排除解释、具体改动、预期变化的指标，以及可能代价。“优化内存”或“试大一点的 block”不能单独构成假设。

默认每版检验一个主要假设，从当前最佳实现出发。多个修改必须共同验证时，说明组合理由；依赖其他版本结构、探索组合、分支尚未验证或已有证据支持时，可以从其他版本继续，记录原因。

避免重复等价失败方案。实现、组合、输入条件变化，或上次测量无效、受噪声影响、只覆盖部分条件时，才说明差异后重试。多个独立假设可分支探索，按证据、关键未知、收益、成本和重复程度选择；每条分支都经过完整验证。

先检查测量、实现和输入，再据结果支持、否定或修正假设。有可检验的新判断且预算允许时返回实现；证据不足先补测，不盲试参数。

### 6. 停止探索与最终验证

每轮记录后检查以下条件，失败步骤无法继续时同样适用：

| 停止条件 | 依据 |
| --- | --- |
| 达到目标 | 正确性通过，实测达到预定指标 |
| 收敛 | 连续多轮有依据的实验不能改善结果，保留相应结论 |
| 预算耗尽 | 已达到约定次数、时间或其他限制 |
| 接近硬件或实现边界 | 有测量支持继续优化收益很小 |
| 当前无法推进 | 必要环境或知识不足、编译/运行异常未解决，或无法形成可验证假设 |

未达到停止条件时继续迭代；停止时保留最佳实现和未解决问题，再按“校验”完成最终验证。

## 输出

各阶段记录随版本保存在项目中，标明来源版本及失败、回退、未验证或淘汰状态；最佳实现单独标明并关联证据。记录任务使用的包版本、内容标识和快照。

先交付实现、最终正确性与逐输入性能，注明输入范围和基线；再说明关键改动、停止原因和限制，并提供实验记录与复核入口。性能结论须有对应实测，推测单独说明，不在回复中逐轮复述日志。

向统一入口提供已用知识、实现版本、验证范围、关键结果及方法改进依据。本能力不另写反馈或修改公共 Wiki、来源和源 Skill。

## 校验

对最佳实现的确切版本，在约定硬件和正式协议下重新运行正确性检查与测速，覆盖全部必需输入。核对代码、配置、日志和报告一致，使用本次最终数据，不拿历史最佳数字代替。

最终失败或结果不可复现时，记录并返回相应步骤。预算或环境不允许继续、没有合格版本或无法最终评测时，交付已有代码与证据，明确未通过最终验证。
