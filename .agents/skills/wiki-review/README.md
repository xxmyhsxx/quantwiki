# wiki-review

## 1. 任务与设计目标

### 1.1 任务

对用户指定范围内的 Wiki 进行审核，检查事实、证据、格式、链接、内容深度和跨页一致性等方面的问题，主动发现并提出关键知识缺口，形成有依据的审核结论与具体修改建议。

审核对象包括 Wiki 当前的页面内容、结构，以及页面之间的关系。页面、主题、一次变更涉及的内容和整个 Wiki 都可以成为审核范围；变更记录用于辅助定位，不是执行审核的必要条件。

### 1.2 执行者

执行者具备当前 Wiki 主题所需的专业知识，能够理解正文、识别可疑主张、分析知识依赖，并提出必要的检查问题。

领域知识用于形成判断和查证方向。Wiki 是否已有某项知识、来源是否支持某项主张、某个引用编号是否正确，必须依据实际读取或核验的材料判断。审核者自身知道某个机制，不能证明页面已经解释了这个机制。

### 1.3 关键问题、质量目标与方法

| 审核维度 | 需要解决的问题 | 可观察的质量依据与关键方法 |
| --- | --- | --- |
| 事实与幻觉 | 错误或臆补的事实可能表述流畅，仅凭阅读印象容易漏检。 | 对核心结论、关键数字、公式及重要归因主动定向核验，检查它们与原件及其条件是否一致；其他内容结合疑点与抽样检查。 |
| 证据与引用 | 有来源登记、有效路径或引用编号，不代表证据实际支持正文。 | 将主张与对应来源内容对照，区分作者报告、教学解释、代码阅读和实际实验；核验引用标识、位置和来源记录。 |
| 格式与结构 | 路径、frontmatter、表格、公式或段落结构错误可能影响读取和使用。 | 依据项目现行规范，结合机械检查与上下文阅读定位问题；工具未覆盖的结构关系由人工阅读判断。 |
| 链接与关联 | 链接存在但目标不承接所需知识，或者已有内容没有建立必要连接。 | 实际读取相关目标页，并围绕明确问题做关键词、别名或来源检索，区分内容缺失和导航失效。 |
| 内容深度与完整性 | 内容可能保留了结论，却丢失必要机制、步骤、假设、条件或反例。 | 按页面承担的内容检查解释是否存在关键断点，指出具体缺失及其影响；必要时用代表性问题进行阅读检验。 |
| 跨页一致性 | 不同页面的术语、定义、结论或适用条件可能存在未解释的差异。 | 对照相关页面及其来源，先辨明对象、版本和条件，再判断是否构成冲突、过时概括或需要补充的边界。 |
| 关键知识缺口 | 指定主题所必需的知识可能在现有页面中完全没有被提及。 | 依据领域知识提出候选缺口，说明必要性，检索实际 Wiki 后确认承接情况，再给出缺口及补充位置建议。 |

以上维度按当前范围和内容适用，不要求每一页具有相同栏目，也不按篇幅、标题数或链接数判断质量。审核质量体现为发现有依据、定位具体、结论与覆盖范围相称、建议能够处理实际问题；没有问题时不凑缺陷。

## 2. 使用边界

### 2.1 使用时机

用户要求审核本项目 Wiki、指定页面或主题的内容质量、事实与引用、格式、知识关联、解释深度或知识缺口时使用。用户明确要求审核一次 ingest 成果时，也可以将其涉及的 Wiki 内容作为范围。

普通 Wiki 查询和写入后的例行自检不自动触发本 Skill。正式有用性对照评测不属于本 Skill；代表性问题的阅读检验只用于辅助内容判断。

### 2.2 范围与修复

- 从用户指定范围开始，沿相关链接及具体待核问题定向扩展。检索其他位置只为解决当前问题，不自动转为全库审核。
- 全库结论需要相应覆盖。抽样审核说明样本、选取依据与未读范围，不把局部结果推广为整个 Wiki 的结论。
- 默认只读审核。用户同时要求修复时，直接处理已授权、低风险且范围明确的问题；重要取舍按已确认的项目约定讨论。
- 发现缺口后交付缺口及建议，不自动启动论文 ingest、正式评测或全库整理。
- 仅要求创建或修改本 Skill 时，不开始实际 Wiki 审核。

## 3. 输入设计

输入以用户请求和项目现状为准，不要求用户填写固定表单。

| 输入 | 用途与读取方式 |
| --- | --- |
| 审核目标与范围 | 确定待审页面、主题或整体范围；用户指定的重点和修复要求优先采用。 |
| Wiki 正文与相关页面 | 审核的主要对象。先读范围内内容，再按具体问题补读必要关联页。 |
| `wiki/README.md` 等项目规范 | 判断命名、结构、引用和组织约定。复用已读且未变化的规则；规则不清楚时只补读相关章节。 |
| 页面 `sources:` 与对应原件 | 定向核对主张、引用及实现依据。原件可包括论文、LaTeX、代码文件和实验材料。 |
| 来源条目的 `README.md` | 读取论文编号、版本、commit 等来源记录，识别缺失或冲突。 |
| 已有检查结果、变更信息 | 存在且仍适用时复用，用于减少重复检查和定位相关内容。 |

项目路径以实际项目根目录为基准。整个 `raw/` 库不是审核前置输入；也不自行要求独立来源页、能力自述页、固定日志或全套模板。必要材料不可得时，继续完成不依赖这些材料的审核，并明确相应核验限制。

## 4. 原则设计

1. **依据实际材料判断。** 不凭记忆断言 Wiki 已有或缺少内容，不把来源登记、脚本通过或模型自身知识当作事实已核验的证据。
2. **问题性质与核验状态分别说明。** 区分事实错误、证据缺口、解释不足、结构问题和可选优化；对相关事实说明已核验、部分核验或未核验。未完成查证不能直接判为幻觉。
3. **区分规范问题与改进建议。** 违反现行规范时指出对应依据；其他问题给出内容、证据或知识依赖上的理由。不能把审核者偏好的写法当成项目硬性要求。
4. **检查必要深度。** 深度依据当前内容的职责判断。指出具体缺失及其影响，不强求每页都具备推导、反例、消融和实现教程。
5. **主动提出必要缺口。** 除审核已写内容，还要发现指定范围内未提及的必要知识；先说明必要性并定向查找，再提出缺口，避免将普通延伸知识都判成缺陷。
6. **保留知识价值。** 压缩、合并或删除建议必须说明机制、独特证据、条件、反例和链接用途的保留与承接。基础知识不能因“常见”被判为低价值，无法证明承接完整时保留原内容。
7. **结论不超出证据和范围。** 如实说明读了哪些页面、核了哪些主张、哪些内容未核验；不输出没有评分依据的总分或无范围的整体通过结论。

## 5. 工作流程设计

### 5.1 确定范围和审核依据

结合用户请求确定审核入口、重点、修复授权及适用规范。阅读范围内页面，识别它们承担的内容以及需要核对的来源和关联。

已有规则和检查结果仍适用时复用。主题或全库审核需要明确实际覆盖方式；采用抽样时说明选取理由，并把内容阅读范围、机械检查范围和原件核验范围分别记录在审核过程中。

范围不明确且会影响实际工作时再澄清；不为已经明确的信息重复提问。

### 5.2 检查格式、路径和结构

先判断是否需要新增机械检查，需要时合并安排以下检查入口，避免在不同步骤反复运行：

```bash
python3 .agents/skills/wiki-review/scripts/check_wiki.py --root .
```

从项目根目录运行随包工具 [scripts/check_wiki.py](scripts/check_wiki.py)。工具只读，仅依赖 Python 3.9+ 标准库，检查目录、frontmatter、标签、链接与锚点、表格结构、来源路径、arXiv 登记一致性和导航；输出 JSON，发现错误时返回非零退出码。缺少 `raw/` 时明确跳过本地来源核验，要求来源完整时加 `--require-raw`。只在需要相应机械检查时运行，不要求每次维护都做全库检查。

脚本不核实科学主张或引用编号，也不覆盖所有来源登记和内容问题；按本轮范围补充直接核对，不另建同功能工具。

结合输出确认范围内的问题。孤立页等提示还需结合实际用途判断，不能把所有工具提示直接等同于内容缺陷。工具产生的范围外结果不自动扩大本次处理范围。

机械检查之外，阅读段落上下文，检查公式、表格、列表与引导句的关系。工具缺失或不能运行时，采用可完成的直接检查，并说明覆盖限制。

### 5.3 审核事实、证据和引用

主动围绕核心结论、关键数字、公式和重要归因进行定向核验，避免只回查读起来可疑的内容。其他内容结合疑点和抽样检查；范围较大时说明选择依据，未覆盖部分保留为未核验。

对待核主张，先读所在段落的上下文及条件，再依据 `sources:` 找到相应原件，核对主张、适用对象、限制与证据之间的关系。重点识别：

- 来源中没有相应支持，却写成确定事实或作者结论的内容。
- 数字、公式、对象、因果或归因与原件不符。
- 作者报告、代码阅读、教学解释、计划验证与实际实验混用。
- 精度、存储、算子性能和端到端收益之间存在未经支持的推导或替代。
- 来源中的条件、反例或限定被省略，导致正文结论扩大。

引用核验采用以下规则：

1. **来源标识从本地记录读取。** 论文编号、版本、commit 从来源条目的 `README.md` 取得，不凭 PDF 水印、记忆或二次来源补猜。本地记录与原件不一致或记录缺失时，报告来源元数据问题，不直接猜改知识页。正文与记录一致只说明登记一致。
2. **具体编号回查原件。** 章节、附录、表、图和算法编号回到 LaTeX 或 PDF 核对。抽取文本未包含对应内容时，不能据此认定原件没有该内容或编号。内容已核实但编号无法确认时，可以建议按内容定位；内容本身未核实则保留待核状态。
3. **直接使用的来源需要登记。** 按项目规范在 `sources:` 登记直接使用的原始材料具体文件；本地 `raw/` 路径留在 frontmatter，不在知识正文中链接或嵌入。正文就近以版本、章节、图表或代码位置定位证据，并在“来源身份”保留标题、版本和外部 URL。检查引用是否由登记材料承接，纯举例与实际来源引用分开。
4. **登记通过与事实核验分开。** 机械检查通过不证明来源内容、引用编号或主张正确；需要逐项核对的编号仍由原件查证。

回查后分别说明确认的错误、证据不足的主张和未完成核验的内容。原件不可得或暂时找不到依据时，不直接判为已确认幻觉；已确认来源冲突时，准确报告冲突发生在哪一层。

### 5.4 审核深度、关联和跨页一致性

围绕页面负责讲述的内容，检查核心问题、符号、公式、机制、推导和算法步骤之间是否连贯，以及必要的假设、反例、消融和实现条件是否被遗漏或过度压缩。只检查适用于该内容的项目。

发现解释断点时，读取相关前置页，判断它是否实际承接了缺失环节。已有页面能承接的，优先提出连接或定位建议；目标页也缺少内容的，指出应补充的位置。必要时选少量代表性问题沿正文与链接检验，把无法完成的解释落实到具体断点。

阅读相关页面时，核对术语、定义和结论的差异是否由对象、版本、条件或证据层级造成。合理差异应明确边界；无法由这些差异解释的矛盾，才作为跨页一致性问题。结合实际发现判断相关旧页是否需要增加实例、修正概括或补充条件。

### 5.5 主动发现并提出关键知识缺口

依据领域知识，检查指定页面或主题是否缺少理解机制、支撑结论、判断适用条件或使用该知识所必要的内容，包括现有页面完全未提及的知识。

对每个候选缺口：

1. 说明需要什么知识，它与当前内容存在什么依赖，以及缺失会造成什么具体影响。
2. 围绕概念、别名、方法或来源定向检索 Wiki，补读直接相关的命中内容；不能仅因当前页没有链接就认定知识不存在。
3. 根据实际查找结果，区分已有内容但连接不足、已有内容深度不足、相关内容缺失，以及当前查找不足以确认的情况。
4. 提出补充建议，说明需要补到什么程度、适合由哪个现有页面承接，或为什么需要新增页面。范围有限时使用“本次查找范围内未找到”等与证据相称的表述。

是否纳入关键缺口取决于其必要性，不以“与主题有关”作为充分依据。普通延伸内容可列为可选建议。缺口审核的产出是发现、依据、影响和补充建议。

### 5.6 整理发现，按授权修复

合并针对同一问题的重复发现，保留各受影响位置。每项发现给出具体依据、影响和最小修改方向，区分现行规范问题与可选优化，明确核验状态。

提出压缩、合并或删除时，先列明必须保留的内容与承接位置；无法证明承接完整时保留原内容。

用户已授权修复时，处理范围明确的相应问题，并对直接受影响的内容做必要验证。插入段落后回看前后各一行，并在需要时扩展到完整段落，确认没有截断“引导句—公式／表格／列表”的关系。涉及编号或来源的修改重新核对相应依据；合并修改后按需运行相关机械检查，避免逐处重复运行。

## 6. 输出设计

默认在对话中交付审核报告，用户要求文件时再落盘。报告包括：

- **实际范围与核验情况：** 审核的页面或主题、补读范围、抽样依据、机械检查及复用结果、实际回查的主张数量和类型、未读与未核验部分。
- **已有可用内容：** 简要说明本次确认可用或无需修改的内容，不逐页凑评价。
- **审核发现：** 问题、证据与具体建议；将规范违规和可选改进分开，事实或内容错误给出相应的确认依据。
- **关键知识缺口：** 必要性、查找范围、当前承接情况、影响、补充内容与建议位置。可并入对应发现，不要求重复报告。
- **修复结果：** 仅在实际修复时说明修改范围、必要验证及保留内容的承接情况。

每项发现至少让用户能够判断：

| 要素 | 内容 |
| --- | --- |
| 位置 | 具体页面与章节、段落或相关页面组合；主题缺口说明其所属范围。 |
| 发现与依据 | 问题具体是什么，依据来自哪条项目规范、哪处来源内容、页面对照或知识依赖。 |
| 核验状态 | 已核验到什么程度，还有哪些部分未确认。 |
| 影响 | 会造成什么事实误解、使用限制、解释断点或导航问题。 |
| 最小建议 | 如何修改、连接或补充；涉及承接时说明位置与保留内容。 |

以上是报告应表达的信息，不强制固定表格或独立日志。无问题时直接报告范围和结果。阅读检验不输出无依据的总分，也不作为正式对照评测结果。

## 7. References 设计

当前设计不新增 `references/`。执行必需的审核方法写入 `SKILL.md`；项目规则、来源材料和检查脚本作为按需读取的项目依赖，不复制成另一套规范。

后续确有较长、可复用的方法材料时再单独设计，并在使用它的步骤明确读取条件和用途。

## 8. 校验设计

### 8.1 设计与实现一致性

实现时核对以下内容是否落实为具体动作和判断：审核对象与范围、各审核维度、主动查证、定向检索、必要知识缺口发现、核验状态、引用规则、报告要素与修复边界。

检查 README 与执行规范是否一致，是否误加固定模板、无依据阈值或不必要文件，以及是否把机械通过扩大为内容正确。

### 8.2 必要场景检查

| 场景 | 预期检查行为 |
| --- | --- |
| 表述流畅的错误数字或归因 | 关键主张仍进入主动核验，发现后报告与原件的具体差异。 |
| 机械检查通过，但引用不支持主张 | 继续进行内容判断，不将工具结果视为事实核验。 |
| 原件不可得，或只核实了内容而未确认编号 | 如实保留未核验部分；按内容定位仅解决编号定位问题。 |
| 本地来源记录与正文一致，但记录与原件冲突 | 报告来源元数据冲突，不以登记一致判为准确。 |
| 链接存在但目标缺少所需内容，或相关内容存在却未链接 | 实际读取并定向检索，分别识别内容不足和连接问题。 |
| 内容正确但缺失必要机制，或主题完全未提及关键知识 | 说明必要性和影响，查找承接内容后提出有范围的缺口建议。 |
| 跨页结论不同，但使用条件不同 | 先核对条件，避免将合理差异误报为矛盾。 |
| 局部审核遇到范围外工具结果，或本轮未发现问题 | 保持任务范围；无问题时据实交付，不凑缺陷。 |
| 已授权局部修复或提出合并删除 | 只处理相应范围，验证相关改动，并检查知识承接。 |

按实际变更选择必要场景，不要求每轮全部执行。场景推演需要说明判断依据；真实运行需要实际输入、输出或工具结果。README 阶段检查设计完整性与一致性，实施后的真实审核另据实际材料验证。

## 9. 文件结构

实现阶段采用以下最小文件结构：

| 文件 | 职责 |
| --- | --- |
| `wiki-review/README.md` | Skill 的设计文档，说明任务、目标、边界、方法、流程、输出与校验。 |
| `wiki-review/SKILL.md` | 依据确认后的 README 编写的实际执行规范。 |
| `wiki-review/scripts/check_wiki.py` | 项目已有的只读机械检查工具，按需复用。 |
| `wiki-review/agents/openai.yaml` | 技能展示配置与调用策略。 |
| `wiki-review/assets/icon.svg` | 技能展示图标。 |

当前设计无需额外的模板、日志、评分器或测试目录。`wiki/README.md` 和 `raw/` 属于目标项目，按实际项目位置访问。
