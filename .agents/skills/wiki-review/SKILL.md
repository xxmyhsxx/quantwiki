# Wiki 审核

## 任务

判断指定 Wiki 是否让读者理解对象的作用、整体工作方式与关键依据。仅要求审核时报告问题；要求修复、重写或改善表达时，在授权范围内交付改好的正文。

## 输入

从请求确认页面或主题、重点和修复要求，读取范围内正文及现行规范。复用已读且有效的规则与检查结果，按具体问题补读关联页，不把整个 raw 或历史日志作为前置输入。

## 原则

领域知识用于提出疑点和识别依赖，不能代替正文或原件。事实正确不等于解释充分；按页面要回答的问题判断深度，不按篇幅、标题数或个人写法偏好判缺陷。

## 工作步骤

### 1. 确定范围

分别记清正文阅读、原件核验与机械检查范围；抽样说明选取依据和未覆盖部分，全库结论须有相应覆盖。范围不清且会影响工作时再询问。仅查链接时直接进入第 4 步。

### 2. 检查解释、关系与缺口

先以未读原论文或源码的目标读者身份读正文，判断能否说清：对象在所属任务中解决什么问题、改变哪个环节、为什么有用及付出什么代价；再看整体怎样工作、关键部分为何存在和如何配合。局部页说明与相关计算或系统的关系即可，不重述全系统或凑齐栏目。不能只在开头补一句用途，后面仍让读者自行拼接机制。

发现理解断点时读相关页，确认它是否真能补足解释。必要时用少量代表问题沿阅读路径检查，指出具体缺失及影响，例如“列出了编译入口，却没说明产物由谁使用”，不只说“缺少宏观视角”。

即使局部事实均正确，也检查解释顺序和段落作用：定义是否晚于使用，主流程是否被特例打断，公式、表格和案例是否支持当前问题，是否重复了别处已有的具体细节。区分缺少知识、关系未讲清和单纯措辞含混，避免把内容问题缩成换词建议。

跨页差异先核对对象、术语、版本、条件和证据；合理差异保留边界，无法解释的矛盾才报问题。补充解释后检查受影响的旧概括、限制说明和研读记录是否仍准确。

还要检查当前范围所需、但正文完全没提到的知识：先说明缺少什么及其影响，再用名称、别名、机制或来源定向检索并读候选正文。区分已有但连接不足、解释不足、确实未找到和查找受限；普通延伸知识列可选建议。给出所需内容、深度及合适页面，不因当前页没链接就断言全库没有。

### 3. 核验事实与证据

主动回查核心结论、关键数字、公式和重要归因，不只查读起来可疑的句子；其他内容按疑点或说明过的抽样范围检查。

1. 读清主张的上下文、对象与条件。根据 `sources:` 找到来源条目，从其 README 读取身份、版本和 commit，不凭记忆或 PDF 水印猜填。
2. 定位原件内容，核对数字、公式、因果、归因与支持范围。作者报告、教学解释、代码阅读、计划与实测分别说明；精度、存储、算子速度和端到端收益不能混用。
3. 章节、附录、表、图、算法编号回到 LaTeX 或 PDF 核实。抽取文本缺内容不证明原件没有；内容已核而编号不明时可按内容定位，内容未核仍保留待核。
4. 按项目约定核来源登记。本项目每页按固定来源目录登记，同版本只列一次，raw 路径留在 frontmatter，正文保留章节/函数等定位与行内代码形式的来源 URL。纯举例与实际引用分开。

来源记录缺失或与原件冲突时报告元数据问题，不猜改正文。

结果区分确认错误、证据不足和未核验。材料不可得时完成其余检查，说明限制，不直接判为幻觉。来源冲突说明具体差异及未解决部分。

### 4. 检查格式与链接

需要机械检查时，确认目标项目的脚本与范围，从项目根目录运行已有 [scripts/check_wiki.py](scripts/check_wiki.py)：

```sh
python3 -B .agents/skills/wiki-review/scripts/check_wiki.py --root .
```

工具只读，依赖 Python 3.9+ 标准库，检查目录、frontmatter、标签、表格、路径、锚点、来源登记、arXiv 一致性及导航。输出 JSON，错误退出非零；`--strict` 使待核项也退出非零。缺少 raw 时跳过本地来源核验，要求完整来源时加 `--require-raw`。

只查链接时用 `--links-only`，默认全 Wiki，`--paths` 可限定 Wiki 内文件或目录，例如：

```sh
python3 -B .agents/skills/wiki-review/scripts/check_wiki.py --root . --links-only --paths wiki/README.md
```

`--raw-links-only` 单独检查 raw 的无链接存储规则，不读封存原文和 Git 对象；它与 Wiki 链接模式互斥，不接受 `--paths`。具体存储与点击规则以目标 Wiki 规范为准。

移动、删除文件或改标题时检索旧路径和锚点，将回链纳入检查。无效或空路径选择不能算通过。按本次范围读取工具错误、待核项和覆盖限制；孤立页等提示需结合用途判断，范围外输出不自动扩大任务。工具不可用时做能完成的直接检查，不另建同功能工具。

逐条读取新增或变更链接的源段落和目标内容，判断读者需要什么、目标是否回答、删去会损失什么。存量抽样说明未读范围；不凭标题或连通度删链接，也不要求双向链接。静态锚点检查不能证明客户端跳转正常，兼容提示保留待核。

**仅要求链接检查时，到此形成范围明确的报告**，区分失效、越界、用途不成立和待核项；不自动进入科学主张审核。全面审核将这些结果与前述解释、证据检查一起处理。

### 5. 整理发现与修复

合并同一问题的重复发现，保留受影响位置。每项给出依据、核验状态、影响和最小建议；规范违规指出条款，写法偏好作为可选建议。无问题时如实报告，不凑缺陷或无依据总分。

压缩、合并或删除建议须说明独有机制、条件、证据、反例和有用链接如何保留；无法保证保留完整时不删。基础内容不能只因常见而被判低价值。

已授权改善时，先确定页面要回答的问题和解释顺序，再修改正文：补清用途与因果，把必要定义移到首次使用前，沿整体工作过程组织机制，把特例放回对应环节，合并重复案例和说明。需要时重写段落或调整章节，不止于补一句提示、换几个词或留下建议；已有清楚的部分保留，不为统一外观重写。

用具体对象和动作表达，让每段承担必要的解释；先查清说不清的关系，不用抽象术语掩盖。修正后按原有规范核对事实与条件，同步受影响的概括、引用和回链。重要取舍遵循项目约定，验证按影响范围合并进行，不逐处重复跑全库检查。

## 输出

仅审核时，给出发现、位置、依据、影响及建议。已授权改善时，以改后的正文为成果，简述修好了哪些理解断点、核验范围和剩余问题，不能只交问题清单。相同问题合并说明；审核记录仅在用户或项目要求时落盘，不逐页生成报告。

## 校验

仅依据正文及必要链接，重新解释对象的用途、整体过程和取舍；若仍需借原件或执行者未写出的知识才能接上，解释就仍不充分，已授权改善时继续补足。逐段检查内容是否必要、对象和指代是否明确；如有修改，对照原文确认没有丢失机制、证据、条件和不确定性。

检查相邻段落与公式、表格、列表的衔接，核对受影响的引用和回链。审核覆盖、事实核验与正文改善分别如实记录；要求改善的页面不能仅因读过、没有事实错误或已列出建议而标为完成。
