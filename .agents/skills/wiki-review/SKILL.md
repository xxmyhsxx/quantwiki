# 审查 Wiki 质量

按用户指定范围检查知识是否可理解、可追溯、可使用，区分规范问题与质量改进建议。默认只读审查；用户同时要求修复时直接处理已授权、低风险且范围明确的问题，重要取舍按项目约定讨论。

## 范围与必要材料

- 从指定页面、主题或本轮变更开始，只沿相关链接扩展；全库结论需要相应覆盖，抽样审查须说明样本与未读范围。
- 规则不清楚时只补读 [Wiki README](../../../wiki/README.md) 的相关章节；复用已读且未变化的规则，不要求独立来源页、能力自述页、固定日志或全套模板。
- 默认检查知识正文与证据定位。判断某项主张是否准确需要原文时，按 sources 定向核对并记录范围；不把整个 raw 库作为审查前置条件。未回查的事实不得标为原文核验通过。

## 结构与内容分开判断

- 涉及命名、链接或来源路径时，复用仍适用的检查结果，按审查范围补充必要核对。路径与链接有效不证明来源内容正确；局部审查不顺带扩大任务。
- 需要全库结构检查时，使用随包工具 [scripts/check_wiki.py](scripts/check_wiki.py)。从项目根运行 `python3 .agents/skills/wiki-review/scripts/check_wiki.py --root .`；检查标签、元数据、链接、来源路径与导航，输出 JSON，发现错误时返回非零退出码。缺少 raw 时明确跳过本地来源核验，要求来源完整时加 `--require-raw`。工具只读、仅依赖 Python 3.9+ 标准库，不代替内容审查，也不要求每次维护都运行。
- 检查核心问题、符号、公式、推导、算法步骤是否连贯；关键假设、反例、消融与实现条件是否被过度压缩。不能用篇幅、标题数量或链接数量代替判断。
- 检查主张与证据是否相称：作者报告、代码阅读、教学解释与实际实验有无混用；精度、存储、算子性能与端到端收益有无混淆。
- 检查链接是否解释前置、机制、实现或比较关系，目标页是否真的提供所需内容；判断相关旧页是否需要增加实例、修正概括或补充边界。先区分知识缺失和导航失效，避免重复 ingest。
- 必要时选少量代表性问题，沿实际页面检验能否解释清楚或支持判断。这是阅读检验，不是独立对照实验，不输出没有评分依据的总分。

## 事实与引用核验

审查涉及事实与引用时，除内容判断外还要核验引用本身。以下规则来自已经发生过的错误类型，写入与审查都适用：

- **元数据以本地记录为准。** 论文编号、版本、commit 从原件旁的 `source.md`／`manifest.md` 读取，不从 PDF 水印、记忆或二次来源推断；两者不一致时先记为来源元数据缺口，不直接改知识页。
- **编号必须回查原件。** 章节号、附录号、表号、图号、算法号在写入前回到 LaTeX 源或 PDF 核对；抽取文本缺表格时应视为「没有编号可引」，改用按内容定位（如「论文的组件消融表」），不写未经验证的编号。
- **正文引用的原件要登记。** 正文直接使用的 `raw/` 路径（包括仓库内被引用的具体文件）应出现在该页 `sources:` 中；仅作举例的路径改成纯文本描述。
- **插入位置要看上下文。** 新增段落不得插在「引导句—公式／表格／列表」之间；写入后回看该段前后各一行，确认没有截断原有的引导关系。
- **合并相关检查。** 按改动范围核对路径、链接、元数据与导航；缺少 raw 时明确说明本地来源未核验。检查通过不表示内容正确，正文中的公式、图表和章节引用仍需按审查范围回查。
- **报告核验范围。** 说明抽了多少条、覆盖哪些页面、哪些没有核（例如只出现在图中、或原件不可得的数字），不做无范围的整体结论。

## 整理建议与交付

涉及压缩、合并或删除建议时，先标出必须保留的机制、独特证据、条件、反例与链接用途，以及它们的承接位置。基础知识不能因“常见”被判为低价值；不能证明承接完整时保留原内容。

报告实际审查范围、已有可用内容与主要问题。每个问题给出具体页面/章节、证据、影响和最小修改建议；将违反现行规范与可选优化分开，未验证部分明确说明。无问题时直接报告范围和结果，不凑缺陷。

发现缺口不自动启动论文 ingest、正式评测或全库整理。若已授权修复，合并修改后只做必要验证，并说明保留内容的承接情况；报告默认在对话交付，用户要求文件时再落盘。仅要求创建或修改本 Skill 时，不开始 Wiki 审查。
