# Wiki Kernel Writing

## 1. 任务与设计目标

### 名称与定位

Skill 名称为 **`wiki-kernel-writing`**，中文名称为 **算子编写**。

`kernel-writing` 直接描述任务：把参考实现写成 GPU 算子，并通过实际验证、测量和必要迭代完成交付。`wiki-` 只作为 Skill 系列的命名前缀，不表示执行时需要访问 Wiki，不绑定任何具体仓库或知识库。

本 README 是 Skill 的当前设计文档；[SKILL.md](SKILL.md) 是执行规范。设计文档解释任务、质量目标、方法与边界，执行规范给出具体动作和判断。执行所必需的流程不得只留在 README 或未随包交付的对话中。

### 角色与任务

执行者是具备 CUDA/Triton 编程和 GPU 算子分析能力的编码 Agent。它需要阅读当前项目的代码、测试和运行环境，通过工具完成实现与实验，而不是只提供代码建议。

任务是：

> 根据可信 Reference、目标 GPU、必须支持的 workload、正确性约定、性能指标和优化预算，编写或改写 GPU Kernel，通过可复现的实验循环，交付本次探索中找到的最佳已验证实现。

这里的“写算子”包括从高层实现编写第一版 Kernel，也包括改写和优化已有 Kernel。验证、Benchmark 和必要的 Profiling 是完成这项任务的方法，不是与编写相分离的另一个任务。

“最佳”仅指当前任务、评测条件和已完成探索范围内的 best-so-far，不宣称全局最优。正确实现不自动等于比 Baseline 更快；结束优化也不自动等于完成最终验证。不能完成完整闭环时，交付已有代码、证据与具体阻塞，不能用计划代替运行结果。

### 任务理解与拆解

**先确定究竟要算什么，以及哪些条件不能改。** 高层代码的执行结构不等于 Kernel 的实现结构，但输出语义、必须支持的输入和数值约定必须保持。通过阅读 Reference、调用入口和测试明确这些条件，才能知道代码应该如何实现、如何检查，而不是凭算子名称猜测语义。

**建立真正可用的比较起点。** 没有正确且测量有效的 Baseline，就无法判断新实现是否改善了目标。Reference 负责定义语义，Baseline 负责提供性能比较，两者可以是同一实现，也可以不同；不能为了更容易获得 speedup 擅自更换比较对象。

**先形成可以验证的实现，再迭代优化。** 第一版优先简单、正确、可编译和可测量。每一个实际代码版本都要经过编译、正确性与性能测量，避免复杂改动掩盖错误来源，也避免把旧版本的验证状态带给新代码。

**用实验决定下一次改什么。** Benchmark 提供性能结果；需要解释瓶颈或区分竞争假设时，再使用 Profiling。执行者需要把观测、证据、诊断和可验证假设分开，通过具体改动检查预期指标，而不是看到某个指标就直接套用固定优化。

**保留有效结果，并给出可信的结束依据。** latest 与 best 分开维护，失败和回退实验同样保留。停止优化需要有达标、收敛、预算、边界或阻塞依据；交付前对确切版本重新执行正式评测，报告能够追溯到实际代码和日志。

### 质量目标与关键方法

| 质量目标 | 可观察的判断依据 | 主要方法 |
| --- | --- | --- |
| 语义与正确性可靠 | 交付实现满足已确认的语义和全部 required workload；错误及未验证范围有记录。 | 阅读 Reference 与测试；所有 Candidate 先编译，再对照检查正确性。 |
| 性能结论可信 | 比较来自真实、有效且条件可比的测量；不以单个有利 shape 代替整体要求。 | 固定正式评测入口与协议，先验证 Baseline，再逐 workload 测量。 |
| 迭代有依据 | 每个主要优化能说明观测问题、证据、改动和预期可测变化，并有实验结论。 | 假设驱动；按需 Profiling；默认一次验证一个主要假设。 |
| 结果与过程可追溯 | 能找到 Candidate 的确切实现、parent、通过或失败记录及结论，能够解释 best 为什么改变。 | 随阶段更新实验历史；保存成功、失败和回退版本；独立维护 best。 |
| 工作量受控 | 没有为了填流程机械 Profile、反复运行等价失败实验，或超过已约定预算持续探索。 | 根据证据决定 Profiling；检查实验历史和停止条件。 |
| 交付边界准确 | 报告区分最终通过、历史已验证、推测、未解决和未执行状态。 | 最终 canonical evaluation；核对代码、配置、日志和报告。 |

质量目标通过相关步骤共同实现，不设置与任务无关的固定提升比例、误差阈值或评分。具体 tolerance、指标、整体比较规则和预算以当前任务的有效约定为准。

### 关键术语

| 术语 | 在本 Skill 中的含义 |
| --- | --- |
| Reference implementation | 定义或验证算子语义的可信参考实现，不要求 Kernel 复刻它的执行结构。 |
| Baseline | 任务约定的性能比较实现；只有满足 Candidate 的交付约束时，才可兼任初始 best。 |
| Candidate | 一次可追溯的候选实现，包含实现版本、parent、设计或假设及对应实验结果。 |
| best / latest | best 是当前合格的最佳已验证实现；latest 是最近尝试的实现。二者不能混用，best 也可能暂时不存在。 |
| required workload | 当前任务明确要求支持和验证的输入条件集合，不仅是随意挑选的一组 shape。 |
| canonical evaluation | 当前任务约定的正式正确性与 Benchmark 入口和协议，不指 Skill 内置的一套通用评测器。 |
| References / `references/` | 随 Skill 提供的可选知识或方法材料，与 Reference implementation 不是同一个概念。 |

## 2. 使用边界

### 适用任务

适用于将 PyTorch 或其他高层实现写成 CUDA/Triton Kernel，改写或优化已有 Kernel，以及涉及实际实现与运行测量的算子融合、调度、数据布局和执行策略优化。

Skill 负责确认任务约束、理解语义、建立基线、编写实现、执行验证与测量、按证据迭代、保存实验、判断停止和完成交付。目标 GPU、backend、workload 和评测协议由具体任务提供，不固化为某个项目的路径或命令。

### 不自动处理的任务

仅解释概念、阅读或总结代码、没有实际运行与测量的静态评审，以及不涉及 Kernel 的纯框架层、模型层或业务层优化，不自动进入这套闭环。

没有可执行环境和可信 Reference，且任务也不包含补齐这些条件时，不启动完整闭环。执行中发现必要环境或材料缺失时，只在当前任务范围内补齐；仍无法补齐则明确阻塞阶段，保留已有结果。

### 流程、知识和工具的分工

`SKILL.md` 保存稳定流程、判断、验证门槛、记录与停止条件，不写成具体优化技巧大全。需要固化的优化知识通过离线迭代纳入随包 References；正常执行不临时检索外部 Kernel Wiki。

项目中的编译、测试、Benchmark 和 Profiler 工具属于执行环境。随包脚本只在实际存在且适用时使用，不能假设有一个未提供的测量器或摘要工具。

本版本交付的是完整的流程 Skill，不是一套自带 GPU、编译器、测试数据和所有优化知识的运行环境。没有随包知识材料不等于允许外部检索，也不意味着只要 `references/` 不存在就必须停止；应依据当前项目、工具与实验能否支持继续推进来判断。

## 3. 输入设计

输入不要求用户填写固定表格。优先复用用户任务、当前仓库代码与文档、已有配置、测试、实验记录及可核实的运行环境。

| 输入类别 | 应取得或确认的信息 |
| --- | --- |
| 算子与语义 | Reference implementation、输入输出、调用入口、数学与数值语义、框架集成要求。 |
| 执行环境 | 目标 GPU、backend、可用编译器与运行环境，以及构建和执行入口。 |
| 支持范围 | 必须支持的 shape、动态维度、dtype、layout 和重要边界条件。 |
| 正确性要求 | 可信对照、测试范围、容差及其他必须保持的数值行为。 |
| 性能评测 | Baseline、主指标、指定目标（如有）、正式评测入口、统一测量协议及多个 workload 的整体判断规则。 |
| 预算与限制 | Candidate 数量、Profiling 次数、GPU 时间或当前任务约定的其他限制。 |
| 已有实现与证据 | 当前代码、Candidate 历史、best 标识和对应验证记录。 |
| 可选辅助材料 | 实际随包提供且与任务相关的 References、脚本，以及项目现有工具。 |

必要但未确定的信息标记为 `UNKNOWN`，先从现有材料和环境中解析，不能用记忆补造硬件、测试范围、tolerance、Baseline 或预算。仍然不明确时，需要说明具体缺项和它阻塞哪个步骤；不能为了继续执行擅自改变正确性或比较标准。

本设计不要求每项缺失都阻塞所有工作。应先判断其是否是当前步骤的必要条件；Reference、目标 GPU、required workload、正确性约定、Baseline 与性能指标足够明确后，才能进入依赖这些条件的正式实现和评测流程。

## 4. 原则设计

### 正确性先于性能

每个 Candidate 必须遵守 `Compile → Correctness → Benchmark`。编译或正确性未通过，不进入性能测试，不获得性能结论，也不能成为 best。修改代码后重新验证，对应关系不能跨实现版本复用。

### 结论必须来自证据

性能提升、回退、达标、接近边界和优化有效等判断必须有实际测量支持。领域经验可以用于提出假设，诊断也可以保留不确定性，但不能替代实验结果。

### 评测条件保持可比

不得静默调整 GPU、shape、dtype、layout、tolerance、warmup、测量次数、计时方法、Baseline 或指标。任务要求改变评测条件时，记录变化，重新建立可比数据，不能直接混用新旧结果。

### 实现与实验可追溯

每个有意义的实现版本、改动、假设、结果与结论都能恢复和核对，失败实验也不删除。记录随执行更新，不在结束时凭记忆补齐；不另建重复的状态体系。

### 假设驱动并保护 best

初始版本优先简单正确，后续默认一次验证一个主要性能假设。组合修改、重复实验和从非 best 继续都需要具体理由。更新 best 要同时满足正确性、全部 required workload 和统一协议下的指标改善，latest 的出现不自动替换 best。

### 保持运行时闭包

正常执行使用当前执行规范、实际随包辅助材料、当前仓库和任务记录，以及本地可用工具，不查询外部 Kernel Wiki，不静默扩大依赖。辅助材料按需读取；无法继续时保存 best verified result 和 unresolved issue，留待离线迭代，不把未知写成已解决。

## 5. 工作流程设计

主线为：

```text
确认任务与环境 → 理解 Reference → 建立 Baseline
→ 设计并实现 Candidate → Compile → Correctness → Benchmark / 更新 best
→ 检查停止条件
   ├─ 继续：按需 Profiling → 诊断与假设 → 下一 Candidate → 重新验证
   └─ 结束：最终 canonical evaluation → 交付结果与限制
```

步骤编号用于定位，不要求执行者每轮重走所有准备步骤。验证失败、评测条件变化和探索结束分别按对应路径处理，未执行或失败的阶段不能被记作通过。

### Step 1：确认任务、环境与评测约定

这一阶段解决“本次写什么、在什么条件下算写对和写好”。从任务与仓库取得必要信息，形成可用的语义、workload、正确性、性能和预算约定，确认正式评测入口及现有积累。

多个 workload 的要求和整体比较方式必须在判断改进前明确，防止只挑选一个有利 shape。必要材料不足时说明缺项和阻塞，能在任务范围内补齐的先补齐，不能以默认猜测替代约定。

### Step 2：理解 Reference 与算子语义

结合 Reference、调用入口、测试和相关 build/runtime 代码，明确输入、输出、broadcasting、reduction、动态维度、边界与集成要求。理解结果必须足以支撑实现与测试，而不只是复述函数名称。

这里保留实现自由，但不改变应保持的数值语义。存在影响正确性的歧义时先回到材料核实，避免在后续 Kernel 中固化错误理解。

### Step 3：建立可比较的 Baseline

对约定 Baseline 先确认正确性，再按统一协议测量全部 required workload。记录实现、环境、评测条件、逐 workload 结果和执行入口，形成后续实验的可比起点。

Baseline 不自动等于 best：只有同时满足 Candidate 的交付约束时才可兼任；否则 best 可以暂时不存在。无效 Baseline 需要先处理，不能带着错误或不可比数据评价新实现。

### Step 4：设计并实现当前 Candidate

第一版形成简单、可验证的实现；后续版本执行已经形成的假设和 planned change。给每个 Candidate 保留标识、parent、代码版本与设计说明，不在本轮实现中夹带无关改动。

具体实现知识只在需要时从实际存在的相关 Reference 中读取。实现完成后进入编译；修改后的代码版本必须与新验证记录对应，不沿用旧版本的通过状态。

### Step 5：通过 Compile Gate

编译是进入正确性验证的门槛。通过后进入 Correctness；失败时保存错误、定位与修复，再重新编译，不绕过构建失败进行性能比较。

仅修复编译问题且主要假设不变时，可沿用 Candidate ID 并记录修复；结构或假设有实质变化时，需要可区分的实现记录。无法修复或触及停止条件时保留证据，不无限重试。

### Step 6：通过 Correctness Gate

使用可信 Reference 和约定测试检查当前实现，覆盖全部 required workload，并按适用范围检查代表性、边界、不规则 shape、随机输入、重要数值范围及 dtype。

保留实际测试范围、通过或失败、适用误差和失败条件。失败优先修复并重新经过 Compile，不能放宽 tolerance 换取通过；无法继续时进入停止与受限交付路径。

### Step 7：执行 Benchmark 并判断是否更新 best

只测量已验证 Candidate，使用与 Baseline、best 相同的正式协议，记录 warmup、重复执行、必要同步、汇总方式及逐 workload 指标。

首次合格 Candidate 可以成为首个 best，但不因此宣称超过 Baseline。指标确实更优且全部任务约束满足时才能更新 best；接近噪声范围时在预算允许下复测，无法确认则保留原 best。回退实验保留并标记；测量无效或条件不可比时，先修复评测或重建可比数据。

`accepted` 等本轮结论与 best 标识分开维护。完成记录后检查停止条件，继续优化才进入下一轮证据分析。

### Step 8：判断是否需要 Profiling，并收集必要证据

Profiling 用于回答具体问题，不是每个 Candidate 的固定任务。第一版明显低于目标、连续两个有效 Candidate 未改善 best、出现无法解释的回退、瓶颈不明，或 Benchmark 无法区分竞争假设时，应进行针对性 Profiling；若已有的编译、正确性或 Benchmark 证据已足够定位问题，则直接进入诊断，不增加无必要的分析。

按问题选择实际可获取的指标，优先使用项目工具或已有随包脚本。原始结果保留以便复核，上下文只保留相关摘要；没有摘要脚本时直接整理，不假设工具存在。缺少工具、依赖或预算时说明限制，依据剩余证据决定继续形成假设还是停止。

### Step 9：诊断、形成假设并选择下一 Candidate

将观测、证据、诊断与不确定性分开，形成包含可观测问题、具体证据、可执行改动和预期可测指标的假设，同时说明可能的代价。不把“更快”“优化内存”这类目标词当作完整假设。

创建下一版本前检查历史，避免重复等价失败方案。默认从 best 出发；结构依赖、组合试验、未完成分支或已有证据支持的继续探索，可以从其他版本出发，但需说明理由。多个独立假设可以分支，优先考虑证据、不确定性、预期收益、验证成本与重复程度，每条分支都遵守完整验证门槛。

假设明确且预算允许时返回实现步骤；不足时补测或按需 Profile。仍无法推进则记录 unresolved issue，而不是盲试参数或临时查询外部 Wiki。

### Step 10：检查停止条件

每轮更新记录后检查停止依据；编译、正确性或环境问题造成阻塞时同样适用。允许依据达标、有证据的收敛、预算耗尽、接近硬件或实现边界、当前无法继续推进而结束优化。

停止依据必须具体：不能把随意尝试几次无提升称为收敛，也不能凭感觉宣称已接近上限。停止只决定不再继续搜索，不替代最终验证。

### Step 11：执行最终 canonical evaluation

在约定硬件与协议下，对当前 best 的确切代码版本重新运行正式 Correctness 和 Benchmark，覆盖全部 required workload，并核对报告、配置、代码和日志一致。

全部通过且测量有效时形成最终已验证结果。出现错误、无法复现或不可比较时，记录并返回对应步骤处理；条件不允许继续时，交付当前代码与历史证据并说明未通过最终验证。没有合格 Candidate 或无法完成评测时，不包装为成功交付。

## 6. 输出设计

### 运行中的记录

任务状态、实验历史和 best 状态是需要保留的信息职责，不强制对应三份文件。已有项目记录机制可以复用；没有等价载体时建立足够支持追溯的记录，不追加重复状态表。

**任务状态**保存目标、Reference、环境、required workload、正确性与性能约定、Baseline、预算，以及未明确项和影响。

**实验历史**随执行更新，保存 Candidate 标识与 parent、可恢复实现、改动和假设、编译结果、正确性范围与结果、逐 workload 性能与协议、可选 Profiling 证据、本轮结论及下一步依据。错误、无效、回退和未执行状态都需要如实保留。

**Best 状态**独立记录当前 best 标识、对应实现和正确性与性能证据。没有 best 时明确为空；最新尝试失败或回退不覆盖历史有效结果。

记录格式可以沿用项目已有状态。执行规范提供最小内容要求，不要求强制采用特定 JSON/YAML schema，也不默认建立数据库、实验平台或多份重复日志。

### 最终交付

交付真实实现或可定位的代码修改，附复核所需的测试、Benchmark 入口及实验记录位置。最终报告应能说明：

| 部分 | 需要表达的内容 |
| --- | --- |
| 目标与范围 | Operator、GPU、backend、required workload、dtype/layout、主指标和约束。 |
| Baseline | 比较实现、正确性、逐 workload 性能和统一协议。 |
| Best Candidate | 标识、实现版本、最终正确性和性能、speedup，以及 canonical evaluation 状态。 |
| 改动与实验 | 实际改了什么、为什么改、哪些试验支持或否定假设，包含重要失败和回退。 |
| 结束依据 | 达标、收敛、预算或阻塞等理由及证据。 |
| 限制与未解决项 | 剩余瓶颈、未核实解释、未完成阶段和有依据的后续方向。 |

报告格式服从项目已有约定，但必须区分已测量确认的事实、推测和未解决问题。只有部分阶段完成时，交付已有产物及限制，不填造 speedup、best 或最终通过状态。

## 7. References 设计

### 当前版本

当前包不包含 `references/` 或 `scripts/`。稳定流程、验证判断和记录要求已在 `SKILL.md` 中，不依赖不存在的辅助文件。

这不代表已经覆盖所有 CUDA/Triton 知识，也不代表没有任务运行环境即可执行实验。执行者需要具备相应编程能力，并使用当前项目中实际可用的代码、文档与工具；超出当前能力和材料的阻塞按执行规范记录。

### 后续纳入材料的条件

当某类优化知识、指标解释、方法或示例确实需要稳定复用时，可以在离线迭代中纳入 References。材料应有明确用途和适用边界，并在相关工作步骤注明何时读取、怎样使用；不规定固定知识目录，不为了形式完整新建空文件。

当前流程中，Step 4 在实现问题需要时使用相关知识，Step 8 在指标理解与诊断需要时使用相关材料。References 提供候选方法或理解依据，不代替本次任务的正确性与性能证据，也不通过必读的外部链接重新引入运行时 Wiki 依赖。

脚本同样按实际需要纳入，仅用于具体、可执行的辅助工作。没有脚本时不能虚构调用；缺少必要工具影响测量时，明确该阶段未完成，而不是用文本模拟工具结果。

## 8. 校验设计

### 静态检查

检查名称、目录和元数据一致；`SKILL.md` 包含任务、输入、原则、工作步骤、输出与校验，各部分职责明确。README 与执行规范的边界、关键方法、步骤衔接、记录和交付要求一致，执行所必需的方法没有藏在设计说明或历史对话中。

检查失败分支能否回到相应步骤，修改代码后是否重新验证，Baseline 与 best 是否区分，多个 workload 的整体判断是否有依据。检查 References 和脚本只在实际存在时使用，文件引用没有指向未交付的必读材料。

### 场景检查

优先使用当前任务的代表性输入。没有可运行任务时，可以构造情形沿文本走查，但需要说明这只是场景推演；以下是检查设计，不表示已经运行通过。

| 情形 | 应观察到的行为 |
| --- | --- |
| 从高层 Reference 编写第一版 Kernel | 先明确语义与协议，验证 Baseline，再建立 Candidate，并依次通过 Compile、Correctness、Benchmark。 |
| Baseline 不满足 Candidate 的交付约束 | Baseline 保留为比较对象，best 暂时不存在，不凭基线数据虚构候选结果。 |
| 编译失败或正确性失败 | 保存失败位置和实现，进入对应修复路径；不提前 Benchmark，不放宽 tolerance。 |
| 首个合格 Candidate 仍慢于 Baseline | 可以记录为当前 best，但必须保留真实比较，不能宣称提速。 |
| 新版本性能回退，或多个 workload 表现不一致 | 根据约定整体规则判断，保留实验，不因 latest 更新而覆盖 best。 |
| 评测协议变化、测量无效或差异难与噪声区分 | 重建可比数据或在预算允许下复测；不能确认改善时不更新 best。 |
| 需要 Profiling，但工具或预算不足 | 记录缺口；已有证据足够才继续形成假设，否则保留 best 并说明阻塞。 |
| 没有随包 References、脚本或 summarizer | 不读取虚构文件或调用不存在工具；当前材料可支持的步骤照常进行，不跨边界查询 Wiki。 |
| 重复旧失败方案或从非 best 分支继续 | 检查历史，说明条件变化或依赖理由；所有分支仍经过完整验证。 |
| 预算耗尽、没有合格 Candidate，或最终评测失败 | 明确停止与最终验证状态，交付已有代码和证据，不将停止搜索写成成功完成。 |

### 真实运行验证

具备目标 GPU、可执行 Reference、项目环境和有效授权时，使用实际算子任务跑完整闭环，核查代码、命令、日志、逐 workload 结果及最终报告。性能结果只对应实际运行过的硬件、实现和协议，不外推为其他环境结论。

静态检查、场景推演和真实运行分别报告。流程文档通过结构检查，不代表已生成正确高性能 Kernel，也不代表 Agent 在真实任务中已经遵循了全部规则。

## 9. 文件结构

当前完整包：

```text
wiki-kernel-writing/
├── README.md
└── SKILL.md
```

- `README.md`：当前设计文档，说明任务、质量目标、方法、边界、流程和校验设计。
- `SKILL.md`：实际执行规范，定义触发情境、输入、原则、动作、判断、输出与核查要求。

目录名与 `SKILL.md` 的 `name` 均为 `wiki-kernel-writing`。不绑定某个 Agent 产品、工作目录或 Wiki 仓库；文件如何加载由使用方的 Agent 环境决定。

只有纳入实际有用的辅助材料时，才增加对应 References 或脚本并同步其使用位置。本版本不创建空目录，也不将未来计划列为已交付内容。
