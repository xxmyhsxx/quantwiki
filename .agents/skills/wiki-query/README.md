# Wiki Query

## 1. 任务与设计目标

Wiki Query 是**检索／定位型** Skill：给定一个问题、主题或方法名，定位 Wiki 中真正处理它的知识位置，交付可核对的定位结果——要理解这个问题该读哪里，这些位置各自处理什么。

**核心设计决定：交付定位，不代组织答案。** 机制解释、推导、方法评价与研究建议由用户或调用方完成。查询与解释是两种任务：混在一起会让检索结果被顺带作答污染，用户无法分辨哪些是 Wiki 已写、哪些是回答时补的。

### 任务拆解

| 关键问题 | 为什么影响结果 |
| --- | --- |
| 定位真实位置 | 文件名是唯一英文名称、标题是中文、链接使用相对路径；按原词检索容易落空，进而把「没搜到」当成「Wiki 没有」 |
| 读正文才能判定 | 命中片段与标题只说明出现了同一个词，不能证明这一处处理了该问题 |
| 覆盖同一问题的多页 | 一个问题常由前置、机制、比较、实现、验证等多页承担，只给直接命中会漏掉关键位置 |
| 区分未找到与未核实 | 检索失败、正文不可读与「确实没有」是三种结论，混淆会造成错误的覆盖判断 |

### 质量目标

- 每条定位指向实际读过的正文，并能说明该处处理什么；
- 多页承担同一问题时，关键位置不遗漏；
- 未找到时给出检索词与覆盖范围，而不是笼统的「Wiki 没有」；
- 路径与章节实际存在，可直接打开核对。

## 2. 使用边界

负责：定位知识位置；追踪知识关系给出位置集；说明检索范围与未核实部分。

不负责：组织解释性回答；页面质量审查（`wiki-review`）；论文 ingest 与写页（`wiki-ingest`）；Wiki 覆盖范围外的普通量化问答不触发本 Skill。

默认只读：查询发现缺口或错误只报告，不改页面、不启动 ingest 或审查。

## 3. 输入设计

必要输入是待查对象（问题、主题、方法名或一段待定位的表述）；Wiki 位置在本项目固定。

可选范围限定（子领域、目录、页面集）与粒度（一页／位置集）。默认在全库知识页检索，给足以支撑理解该问题的最小位置集；未要求核验时不回查 raw，也不声称完成原文核验。

## 4. 原则设计

1. **命中不等于覆盖**——判定依据是读过的正文。
2. **定位可核对**——只给实际存在且已读到的文件与章节，不编造。
3. **未找到与未核实分开**——保留检索词与范围，说明更像知识缺口还是定位失败。
4. **只读且只定位**——不改页面，也不越过定位范围代用户解释或给建议。

## 5. 工作流程设计

五步：定知识点 → 两路检索 → 读正文判定 → 按需沿链接补相邻位置 → 交付。

- 检索两路并行走：文件名（英文文件名）与正文（中文标题、术语、机制描述）。不中时补查中英文名、别名、方法名、机制特征与相邻方法名，这是区分知识缺口与定位失败的关键动作。
- 沿正文链接 扩展前置概念、共同机制、比较、实现与验证，链接语法按 `wiki/README.md` 解析；只纳入实际存在且读到所需内容的章节。
- 未找到时说明检索词、范围与补查路径；用户要求核验原文时按 `sources` 定向回查，不扫描 `raw/`。

## 6. 输出设计

定位清单，每条 = 可点击的绝对路径链接 + 实际章节 + 一句「该处处理什么」；按与问题的关系分组排序；结尾交代检索范围与未核实部分。

不含机制解释、推导、方法评价与研究建议。

## 7. References 设计

不设置 `references/`。链接语法与目录规范由 `wiki/README.md` 承担，执行时按需读取其中相关章节。

## 8. 校验设计

静态检查：SKILL 的步骤、输出、原则与本节一致；引用的锚点与示例路径实际存在；不残留「组织回答」的要求。

场景检查（不要求每轮全跑）：术语与页面标题不同名；一个问题由多页承担；Wiki 确实没有该知识；检索失败或正文不可读。

## 9. 文件结构

```text
wiki-query/
├── README.md   # 设计文档
└── SKILL.md
```

无 `references/`。
