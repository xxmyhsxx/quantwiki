# Skill Creator

## 1. 任务与设计目标

Skill Creator 用于创建和修改完整的 Skill。

`README.md` 是 Skill 的**设计文档**，负责描述这个 Skill 应该被设计成什么样。`SKILL.md` 是实际执行规范，`references/` 是工作步骤按需使用的可选辅助材料。

Skill Creator 的核心目标是：

> 先与用户讨论并完成 Skill 设计，再写入 README；README 完成且用户确认后，才实现完整 Skill。

### 任务理解与拆解

设计 Skill 时，首先需要把 Skill 的任务理解清楚，而不是直接按照模板填写内容。

应围绕任务分析：

- **任务目标**：这个 Skill 最终要完成什么。
- **任务拆解**：为了完成任务，需要解决哪些关键问题、阶段或能力，以及这些问题为什么影响结果。
- **质量目标**：什么决定任务完成得好不好，依据什么可观察的结果或证据判断。能够具体则不保持抽象，能够合理量化则进一步量化，但不制造伪指标。
- **关键方法**：为解决关键问题、达到质量目标，可以采用什么方法，在什么条件下采用，以及如何判断是否有效。

Skill Creator 应基于自身领域知识主动进行初步拆解、提出质量维度和候选方法，而不是要求用户自己完成 Skill 设计。分析不能只列阶段名称、质量形容词或方法名称。

对于依赖用户背景才能确定的领域判断、用户偏好、存在多种重要选择，或会明显改变 Skill 设计的内容，应说明初步判断和取舍，再与用户讨论，由用户补充、修正或确认。

任务不需要无限拆解。当任务目标、关键问题、质量目标和关键方法已经足以支撑后续 Skill 设计时即可停止。修改已有 Skill 时，只重新分析本次变更及其实际影响，复用其余已确认的设计。

任务分析最终应落实到 Skill 设计中。质量目标、关键方法可以关联一个或多个原则、工作步骤或校验项，只建立有实际意义的关系，不强制一一对应，也不额外要求映射表。

例如，设计算子开发 Skill 时，“正确性高、充分测试”不足以指导执行。可以将其具体化为：以约定的参考实现比较结果，按目标输入与数据类型确定检查范围和误差要求；每轮优化先检查正确性，通过后才比较性能。这里同一个质量目标同时影响测试设计、优化流程和结果校验，不需要另建一层任务设计文档。

一个 Skill 通常包含：

```text
<skill-name>/
├── README.md
├── SKILL.md
└── references/        # 可选
```

其中：

- `README.md`：Skill 的当前设计文档。
- `SKILL.md`：根据 README 实现的实际执行规范。
- `references/`：可选的格式、模板、知识、规范、示例或其他辅助材料，在具体工作步骤中按需使用。

Skill Creator 操作的是完整 Skill，而不只是 `SKILL.md`。

## 2. 使用边界

Skill Creator 负责：

- 创建新的 Skill，或修改已有 Skill。
- 理解和拆解任务，主动提出质量目标、候选方法及需要用户确认的问题。
- 与用户讨论并形成 Skill 设计。
- 在用户明确授权后创建或修改 `README.md`。
- README 完成且用户确认后，创建或修改 `SKILL.md` 及必要的 References。
- 对最终 Skill 做文档检查和必要的场景检查，说明实际验证范围。

Skill Creator 不应：

- 将设计讨论或对方案的认可视为修改文件的授权。
- 未经用户明确要求创建或修改 README，或未经实现授权修改 `SKILL.md`、References。
- 在修改已有 Skill 时擅自裁决未解释的设计与实现冲突。
- 把本应由 Skill Creator 完成的任务分析和设计工作全部反问给用户。
- 擅自扩大修改范围，或把局部修改变成整份 Skill 的重新设计。
- 为尚未提出的需求预先增加大量规则、步骤、文件或机制。
- 将静态检查或场景推演表述为真实运行验证通过。

其他明确要求以用户为准。

## 3. 输入设计

Skill Creator 接收两类任务。

### 创建 Skill

用户提供希望创建的 Skill 及相关需求。

用户不需要一次提供完整设计。Skill Creator 应先理解任务并主动分析，再针对真正影响设计但尚未明确的问题与用户讨论。

### 修改 Skill

用户提供已有 Skill 和修改需求。

开始修改前，读取已有的 `README.md` 和 `SKILL.md`，结合本轮对话理解当前设计、实现、已完成阶段和授权范围。涉及 References 时，再按需读取相关文件。

对于 README 与 SKILL 的差异，应区分：

- **未解释的冲突**：无法根据用户确认的信息解释的目标、规则、步骤或输出矛盾。停止修改，说明具体差异并询问用户，不自行选择正确版本。
- **本轮待同步的变更**：差异明确来自本轮已讨论、已写入 README 的设计变更。它不是需要重新裁决的冲突，但仍须得到用户对当前 README 的实现确认后才能同步。
- **已授权的实现修正**：用户明确指出实现不符合已确认设计，并授权修正。按该范围处理，不重复询问已经明确的裁决。

如果缺少 README，先说明缺失，基于已有实现和用户需求整理待确认的设计理解，区分文件事实与推断。不能把反推结果当作已确认设计；讨论后按授权流程补写 README，再确认实现。

如果用户已提供完成的 README 并明确要求按该版本实现，复核材料与授权范围后进入实现阶段，不重新开展完整设计讨论。

## 4. 原则设计

### 4.1 用户控制

讨论、写入 README 和实现 Skill 是不同阶段。讨论不等于授权修改文件。

只有用户明确要求创建或修改 README 时，才能写入 `README.md`；只有 README 完成且用户确认继续后，才能创建或修改 Skill 的其余实现。

已经针对当前完成的 README 获得实现确认时，不重复索取同一确认。对于不改变已确认设计的实现修正，用户对该修正的明确指令即对应范围的实现授权。授权不自动延伸到其他版本、范围或后续设计变化。

### 4.2 先理解任务，再设计 Skill

先分析任务目标、关键问题、质量目标和关键方法，主动提出有领域依据的判断，而不是直接套模板或让用户填写问卷。

在任务理解基础上，再检查 Skill 的任务、边界、输入、原则、工作步骤、输出、References 和校验。这些维度是设计检查框架，不是要求用户逐项回答的固定问卷。

### 4.3 主动提出高价值问题

提问应来自对任务和设计的实际分析，优先处理会改变目标、质量标准、关键方法、边界或工作流程的不确定性。

提问时提供必要的初步判断或可选方案，说明差异。已经明确的信息不重复询问，不把自身应完成的分析直接交给用户。

### 4.4 先设计，后实现

创建或发生设计变化时，遵循：

```text
理解并拆解任务
→ 与用户讨论 Skill 设计
→ 用户授权写 README
→ 写入 README
→ 用户确认
→ 实现完整 Skill
→ 校验
```

所有设计变化先落实到 README，再同步到实际实现。

续接任务时复用已经完成的讨论和有效授权，不重走已完成阶段。仅修正实现以符合已确认设计，或调整不影响设计的文字时，不为流程而改写 README；仍须先取得对相应文件修改的明确授权。

### 4.5 README 表达当前设计

README 是 Skill 的设计文档，只表达当前设计。

默认不记录修改历史、旧版本设计、Changelog 或历次修改原因，也不为流程续接额外创建状态文件。

### 4.6 原则与工作步骤分离

原则是整个 Skill 执行过程中始终必须满足的高优先级约束。工作步骤是完成任务时执行的具体动作和判断，必须服从原则。

全局约束不应隐藏在局部步骤中，具体操作也不应无意义地堆入原则。实现时应把设计转成可执行指令，而不是在另一份文件中重复设计说明。

### 4.7 References 按需使用

References 是可选的，不规定统一内部结构，可以保存格式、模板、知识、规范、示例或其他辅助材料。

Reference 应服务于具体工作步骤，并在执行到相关步骤且确有需要时读取，而不是默认全部加载。执行所必需的方法应写入 `SKILL.md` 或明确指向随 Skill 提供的材料，不能依赖未随 Skill 交付的对话结论。

### 4.8 奥卡姆剃刀

在完整满足需求的前提下，使用能够解决问题的最简单设计。

不为尚未提出的需求预先增加规则、步骤、文件、References 或机制。修改时优先调整、合并、替换或删除已有内容，只分析和修改本次变更真正影响的部分，不重写未受影响的设计。

Skill Creator 自身也遵守这一原则。

## 5. 工作流程设计

### Step 1：理解现状与当前阶段

创建 Skill 时，读取用户需求和已有材料。

修改 Skill 时，读取现有 README、SKILL 及需要的 References，按输入设计区分未解释冲突、待同步变更和已授权修正。缺少 README 时，先整理待确认的设计理解。

结合已有对话确定本次要改什么、哪些内容已经确认，以及文件修改授权覆盖到哪一步：

- 尚需设计或变更设计：进入 Step 2，只分析本次相关内容。
- 设计已讨论清楚、等待写 README：进入 Step 4。
- README 已完成、等待实现确认：停留在确认处；收到针对该版本的实现授权后进入 Step 6。
- 已确认 README 和实现授权均具备：直接进入 Step 6。

仅修正不改变设计的实现或文字时，先核对其不影响任务目标、边界、方法、流程或输出约定；复用当前设计，用户对该修正的明确指令即对应范围的文件修改授权。按授权修改并校验，不改写无关文件或追加无关实现流程。

### Step 2：理解和拆解任务

围绕任务形成必要分析：

```text
任务目标
→ 关键问题 / 阶段 / 能力
→ 质量目标
→ 关键方法
```

关键问题应说明为什么影响结果；质量目标应给出可观察的判断依据；关键方法应说明解决什么问题、何时采用和怎样检查效果。

能够合理量化时进一步量化；依据不足时提出待确认的标准或定性判据，不编造阈值。不只写“提升准确性”“充分测试”“持续优化”等无法指导行动的口号。

基于领域知识主动提出初步判断和候选方案。拆解到足以确定关键动作、判断和检查方式即可，不要求每个细节都填齐固定字段。

### Step 3：与用户讨论设计

先给出与任务相关的初步分析、拟采用的方法及必要取舍，再询问真正影响设计但尚未明确的问题，并根据反馈修正。

在此基础上确定使用边界、输入、原则、工作步骤、输出、References 和校验。

对关键质量目标和方法，检查其是否实际影响了执行设计：在哪些相关步骤采用什么动作或判断，依据什么结果检查效果。一个目标可以关联多个原则、步骤或校验项，不强制一一对应，也不要求映射表。

修改已有 Skill 时，未受本次变更影响的部分继续沿用，不重复讨论。关键方法与流程已经清楚、重要不确定性已解决时结束设计讨论。

此阶段只讨论，不创建或修改文件。

### Step 4：确认 README 写入授权

设计讨论完成后，检查是否已有针对本次设计的 README 写入授权。有则继续，没有则等待用户明确要求，不把认可方案当作写入授权。

### Step 5：写 README

获得授权后，根据已讨论确定的设计创建或修改 `README.md`。默认结构见“6. 输出设计”。

“任务与设计目标”应体现必要的任务理解、拆解、质量目标及方法依据，工作流程与校验应体现相应落实。只修改本次设计变化涉及的内容，不为局部变更重写整份文档。

README 只表达当前设计，不记录无关讨论过程。写入完成不代表实际实现已经同步。

完成后请用户确认：

> README.md 已完成，请确认是否根据当前设计创建或修改 Skill。

如果当前完成的 README 已经得到用户明确的实现确认，则进入 Step 6，不重复询问。

### Step 6：实现完整 Skill

确认当前 README 已完成，且用户授权按该版本实现，再创建或修改 `SKILL.md` 及必要的辅助材料。默认结构和元数据要求见“6. 输出设计”。

将设计转化为具体执行指令：关键步骤应让执行者知道依据什么信息、采取什么动作或判断、形成什么结果，以及何时进入下一步。仅在影响执行时补充信息不足、检查失败或其他必要分支，不强制逐步填写固定表格。

不能只把设计目标换个章节重复一遍，也不能把必需方法留在未交付的讨论记录里。任务执行所需内容应存在于 `SKILL.md` 或在相关步骤明确引用的随包材料中。

如设计需要 References，同时创建、修改或删除相应文件，并在具体步骤中写明何时读取、如何使用。仅修改用户授权范围内的实现；发现必须改变已确认设计时，先返回设计讨论，不自行扩展。

### Step 7：校验与交付

先做静态检查，再使用与任务相关的代表性输入做场景检查，具体要求见“8. 校验设计”。

校验发现的实现遗漏、引用错误或格式问题，在授权范围内修正后复查；如果修正会改变用户已确认的设计，先说明问题并请求确认。

交付时说明实际修改的文件、检查方式、结果及尚未验证的部分。静态检查、场景推演和真实运行应分别说明，不因文档结构完整就宣称运行通过。

## 6. 输出设计

### README.md

README 是 Skill 的设计文档，默认结构：

```markdown
# <Skill Name>

## 1. 任务与设计目标
## 2. 使用边界
## 3. 输入设计
## 4. 原则设计
## 5. 工作流程设计
## 6. 输出设计
## 7. References 设计（可选）
## 8. 校验设计
## 9. 文件结构
```

任务设计包含在 README 中，不另建独立任务设计文档。没有实际内容的可选部分不为形式完整而强行增加。

### SKILL.md

默认使用 YAML frontmatter 加 Markdown 正文：

```markdown
---
name: <skill-name>
description: "说明该 Skill 完成什么任务，以及在什么请求或情境下使用。"
---

# <Skill Name>

## 任务
## 输入
## 原则
## 工作步骤
## 输出
## 校验
```

生成时替换占位符。`name` 与 Skill 目录名一致，使用 1–64 个小写英文字母、数字或连字符，不能以连字符开头或结尾，也不能出现连续连字符；`description` 为 1–1024 字符的非空字符串，同时说明用途和使用时机。不强制添加其他元数据字段。

元数据格式依据：Agent Skills Specification（`https://agentskills.io/specification`）。

正文各部分的职责：

- `任务`：定义 Skill 要完成什么。
- `输入`：定义执行时获得的信息和材料。
- `原则`：定义始终必须遵守的高优先级约束。
- `工作步骤`：定义具体动作、必要判断、衔接条件及按需使用 Reference 的位置。
- `输出`：定义最终结果及其格式。
- `校验`：定义检查动作、判断依据和需要报告的验证范围。

正文可根据任务调整，不要求所有步骤使用相同字段。用户另有目标平台或格式要求时，在设计讨论中明确并按确认结果实现。

### References

References 没有固定模板或目录结构。

其具体形式由任务决定，但每个 Reference 都应具有明确作用，并与相关工作步骤建立清晰关系。不要为模板完整而创建空目录或无用途的文件。

### 分阶段交付

设计讨论阶段只提供分析、方案和必要问题；README 阶段交付设计文档；实现阶段交付完整 Skill，并说明实际创建、修改或删除的文件和验证情况。

---

## 7. References 设计

Skill Creator 自身默认不设置 `references/`。

只有当某些模板、知识或辅助材料确实适合独立维护，并需要在特定工作步骤中按需读取时，再增加对应 Reference。

---

## 8. 校验设计

校验保持轻量，但不只检查章节是否存在。

### 静态检查

检查当前阶段和授权是否正确，任务分析是否具体，关键方法是否已落实到相关动作和判断，README 与最终实现是否一致。检查元数据、文件引用、步骤衔接和输出要求，删除明显重复或不必要的复杂度。

修改任务还应对照原文件，确认未改动无关设计，也未遗漏本次变更直接影响的相关位置。README 阶段只检查设计文档；不得为消除待同步差异而提前修改实现。

### 场景检查

优先使用用户提供的代表性输入和已确认的质量要求。没有现成输入时，可构造与任务匹配的检查示例，并明确它是构造示例。

沿关键步骤检查：所需信息能否取得，关键判断是否有依据，步骤能否衔接，结果是否符合已确认的质量要求。存在重要边界或失败分支时，补查相关场景；修改任务重点检查变更路径及直接受影响的相邻步骤。

对于 Skill Creator 自身，以下场景可用于检查，不要求每轮全部重跑：

| 场景 | 预期行为 |
| --- | --- |
| 用户只给模糊需求 | 主动提出具体任务分析和候选方法，只询问真正影响设计的问题；不写文件。 |
| 用户认可方案，但未授权写文件 | 继续停留在讨论或等待授权阶段。 |
| 用户仅授权写 README | 写入设计文档后请求实现确认，不提前同步 SKILL。 |
| README 已更新，用户确认按此实现 | 将本轮已知差异视为待同步变更，直接执行已授权同步，不再误报冲突。 |
| 用户只要求局部修改 | 只分析和修改相关内容，保留未受影响的已确认设计。 |
| 仅收到 SKILL，没有 README | 明确缺少设计文档，提出待确认的设计理解，按授权流程补写。 |
| 存在未经解释的设计与实现冲突 | 说明具体差异并询问，不自行裁决。 |

条件具备且不超出用户授权时进行真实运行；否则只做静态检查或场景推演，并说明限制。推演应能指出支持预期行为的规则，真实运行应有实际输出或工具结果，不能把预期行为本身当作通过证据。

无需默认建立自动评分器、独立测试目录或大型评测系统。检查发现的问题在授权范围内修正后复查；涉及设计改变时重新与用户确认。

## 9. 文件结构

Skill Creator：

```text
skill-creator/
├── README.md
└── SKILL.md
```

如后续确有必要，再增加：

```text
skill-creator/
└── references/
    └── ...
```

Skill Creator 创建或修改的其他 Skill 同样以 README 和 SKILL 为基础，References 根据具体设计按需存在。
