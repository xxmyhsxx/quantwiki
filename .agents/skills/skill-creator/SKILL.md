# Skill Creator

## 任务

创建或修改完整 Skill：README 解释设计，SKILL.md 指导执行，references 保存按需读取的材料。

## 输入

新建时读取需求与材料；修改时先读现有 README、SKILL.md 及受影响的辅助文件。

## 原则

认可方案不自动等于写文件授权；已有授权在对应范围内继续有效。

## 工作步骤

### 1. 确定本次要改什么

按对话确认当前阶段和授权：

| 当前情况 | 处理 |
| --- | --- |
| 仍需确定设计 | 先讨论，获准后写 README；用户确认当前 README 后再实现。 |
| 已确认当前 README 并授权实现 | 直接继续实现，不重复询问。 |
| 用户明确要求局部文字修改，或修正偏离已确认设计的实现 | 按该范围修改，不重做设计流程。 |
| 设计与实现有无法从对话解释的矛盾 | 说明差异并询问；本轮已确认的待同步变更不算此类冲突。 |
| 缺少 README | 先提出设计理解，区分文件事实与推断；获准补写后再确认实现。 |

### 2. 形成设计

主动分析任务要解决什么、关键动作是什么、怎样判断结果。先提供判断和选择，再问会改变目标、质量、方法、成本或边界的问题；已知信息不重复询问。

把质量要求落实为动作和证据。例如算子优化要先与参考实现核对正确性，再按相同协议比较性能；“充分测试”本身不能指导执行。依据不足时用明确的定性判据，不编造阈值。信息足够支持实现即可结束分析。

获准后在 README 说明当前设计及重要取舍，只改受影响部分；完成后按第 1 步的授权状态进入实现。

README 的二级章节依次为：任务与设计目标、使用边界、输入设计、原则设计、工作流程设计、输出设计、References 设计（可选）、校验设计、文件结构。

### 3. 编写执行规范

先决定保留、合并、删除或移动哪些内容，再改措辞。新增规则须对应具体需求或重要风险，检查是否已有规则或工具负责；删除或迁移权限、调用和写入边界前，核对实际实现。

二级章节固定为“任务、输入、原则、工作步骤、输出、校验”。任务写用途，输入写所需材料，原则写全程约束，步骤写动作与分支，输出写交付物，校验写判断结果的方法。同一要求完整写一次；其他位置只在会影响执行顺序时简短引用。没有额外内容的章节可以很短，不补通用常识或未来设想。

用具体对象和动作写指令，说明条件与失败后的处理。例如，把“形成反馈闭环”写成“把发现的问题和证据交给入口记录”。一句话混有多个职责时分开；无法说清对象和关系时先补清内容，不靠换词掩盖。输出要求按实际交付物编写，不要求模型反复汇报流程或自评“严谨、完整”。

README 说明选择的理由，不逐步复制执行规范；执行所需方法放在 SKILL.md 或明确引用的随包材料中，不依赖 README 或历史对话补全。

正文前使用 YAML：

```yaml
---
name: skill-name
description: "说明用途和使用时机。"
---
```

`name` 与目录名一致，长度 1–64，使用小写英文字母、数字和连字符；连字符不能连续或位于两端。`description` 为 1–1024 字符的非空字符串。用户另有平台要求时按已确认要求处理。

辅助文件有实际用途才创建，在使用它的步骤注明何时读取、怎样使用。修改、删除或移动文件后同步相关引用。

## 输出

交付实际文件、主要变化、检查结果与未验证部分。只完成设计时不声称实现已完成，静态检查或推演也不等于真实任务通过。

## 校验

先对照设计核对方法、分支、输出、授权及修改范围，再检查标准章节、元数据、引用和辅助文件。README 应能解释重要选择，SKILL.md 应能独立指导执行。

逐段做删除检查：删掉后，读者是否会少理解一件必要的事，或执行者会漏掉一个必要动作、条件或判断？没有损失就删；已有位置说明过就合并。保留的句子应能直接指出对象、动作和条件；指代不明、术语未解释或需要猜含义时继续改。最后对照原文，确认没有丢失证据、失败处理和授权边界。检查自行完成，不另生成逐句评分表。

用与改动相关的代表性输入检查关键步骤和分支；没有真实输入时可构造场景，但要说明是推演。条件和授权允许时实际运行。发现问题后修正受影响部分；需要改变设计时再讨论。
