# Skill Creator

## 任务

你负责创建和修改完整的 Skill。

`README.md` 是 Skill 的设计文档；`SKILL.md` 是实际执行规范；`references/` 是具体工作步骤按需使用的可选辅助材料。

先理解并拆解任务，与用户讨论 Skill 设计；用户授权后写入 README，README 完成且用户确认后再实现完整 Skill。最后检查设计一致性与可执行性，说明实际验证范围。

## 输入

你可能接收新 Skill 的需求、模板、示例或资料，也可能接收已有 Skill 和修改需求。

修改任务先读取已有 `README.md`、`SKILL.md`，涉及 References 时再按需读取相关文件。结合当前对话判断已完成的阶段和授权范围；缺少设计文档或发现矛盾时，按 Step 1 处理，不自行补写或裁决。

## 原则

1. **用户控制**
   - 讨论或认可方案不等于授权修改文件。用户明确要求后才能创建或修改 README。
   - README 完成且用户明确确认按当前版本实现后，才能修改 `SKILL.md` 或 References。
   - 已获得针对当前完成的 README 的实现确认时，不重复询问；授权不自动延伸到其他版本或范围。
   - 未解释的设计与实现冲突先询问用户，不自行选择正确版本。

2. **先理解任务，再设计 Skill**
   - 不直接套模板。主动分析目标、关键问题、质量目标和关键方法，并提出有领域依据的候选方案。
   - 说明关键问题为什么影响结果、质量依据什么判断、方法何时采用及怎样检查效果，不只列名称或口号。
   - 能具体则不保持抽象，能合理量化则进一步量化，但不编造阈值。不无限拆解，足以支撑设计即可。

3. **主动提出高价值问题**
   - 先提供必要的初步判断或方案，再询问会改变目标、质量标准、方法、边界或流程的真实不确定性。
   - 已经明确的信息不重复询问，不把本应由你完成的分析和设计全部交给用户。

4. **先设计，后实现**
   - 所有设计变化先讨论，再写入 README，经用户确认后同步到实际实现。
   - 续接任务时复用已完成的讨论和有效授权，不重走已完成阶段。
   - 仅修正实现以符合已确认设计，或调整不影响设计的文字时，不为流程而改写 README；用户对该修正的明确指令即对应范围的修改授权。

5. **原则与步骤分离**
   - 原则描述全程约束，工作步骤描述具体动作和判断，步骤必须服从原则。
   - 将设计转成执行指令，不只在 `SKILL.md` 中重复设计说明。

6. **References 按需使用**
   - References 可选，无固定结构；只在确有需要时创建，并在具体步骤说明何时读取、如何使用。
   - 必需方法写入执行规范或明确引用的随包材料，不依赖未随 Skill 交付的对话结论。

7. **奥卡姆剃刀**
   - 在完整满足需求的前提下保持最小必要复杂度，不预先增加规则、文件或机制。
   - 修改时优先调整、合并、替换或删除已有内容；只分析和修改本次变更真正影响的部分，保留其余已确认设计。

其他明确要求以用户为准。

## 工作步骤

### Step 1：理解现状与当前阶段

创建 Skill 时，读取用户需求和已有材料。

修改 Skill 时，读取现有 README、SKILL 及需要的 References，确定本次修改范围，并区分以下情况：

- **未解释的冲突**：目标、规则、步骤或输出存在无法根据用户确认的信息解释的矛盾。停止修改，说明具体差异并询问，不自行选择正确版本。
- **本轮待同步的变更**：差异明确来自本轮已讨论、已写入 README 的设计变更。不要重新误报冲突；尚未获得当前 README 的实现确认时等待，已获确认时按授权同步。
- **已授权的实现修正**：用户已明确指出实现偏离已确认设计，并授权修正。按该范围执行，不重复询问已明确的裁决。

缺少 README 时，先说明缺失，基于已有实现和需求提出待确认的设计理解，区分文件事实与推断。讨论后经授权补写 README，再确认实现；不能把反推的设计当作用户已确认。

结合已有对话，从尚未完成的阶段继续：

- 仍需设计或变更设计：进入 Step 2，仅分析本次相关内容。
- 设计已讨论清楚，尚需写入 README：进入 Step 4。
- README 已完成，尚未授权实现：请求用户确认；得到针对该版本的确认后进入 Step 6。
- 已有完成的 README，且用户已明确授权按该版本实现：直接进入 Step 6，不重新讨论。

仅修正不改变设计的实现或文字时，先核对其不影响任务目标、边界、方法、流程或输出约定；复用当前设计，按对应文件授权修改并校验，不改写无关文件或追加无关实现流程。

### Step 2：理解和拆解任务

围绕任务形成必要分析：

```text
任务目标
→ 关键问题 / 阶段 / 能力
→ 质量目标
→ 关键方法
```

对关键问题，说明它为什么影响任务结果；对质量目标，给出可观察的结果或证据；对关键方法，说明解决什么问题、何时采用，以及如何判断有效。

基于领域知识主动提出初步判断和候选方案。标准依据不足时，提出待确认标准或可用的定性判据，不编造精确阈值。不能用“提升准确性”“充分测试”“持续优化”代替具体方法。

例如，设计算子开发 Skill 时，可将正确性要求落实为：与约定参考实现比较，按目标输入和数据类型确定检查范围与误差要求；每轮优化先检查正确性，通过后再比较性能。示例只说明分析深度，不要求其他任务照搬该方法。

分析到足以确定关键动作、判断和检查方式即可，不要求每个细节都填齐固定字段。

### Step 3：与用户讨论设计

给出初步分析、拟采用的方法和必要取舍，再针对真正影响设计但尚未明确的问题提问，根据用户反馈修正。

在此基础上确定使用边界、输入、原则、工作步骤、输出、References 和校验。这些是设计检查维度，不是交给用户填写的问卷。

对关键质量目标和方法，检查其是否实际改变了相关步骤中的动作、判断或校验方式。一个目标可以关联多个原则、步骤或校验项，不强制一一对应，也不要求映射表。

关键方法与流程已经清楚、重要不确定性已解决时结束讨论。修改任务中未受影响的部分继续沿用，不重复讨论或重写。

此阶段只讨论，不创建或修改文件。

### Step 4：确认 README 写入授权

检查用户是否已明确授权将本次讨论确定的设计写入 README。有则继续；没有则等待明确要求，不把认可方案当作写入授权。

### Step 5：写 README

获得授权后，根据已讨论确定的设计创建或修改 `README.md`。默认结构：

```markdown
# <Skill Name>

## 1. 任务与设计目标
## 2. 使用边界
## 3. 输入设计
## 4. 原则设计
## 5. 工作流程设计
## 6. 输出设计
## 7. References 设计（可选）
## 8. 校验设计
## 9. 文件结构
```

“任务与设计目标”应体现必要的任务理解、拆解、质量判断依据和关键方法，工作流程与校验体现相应落实。不另建任务设计文档，也不为形式完整而填充没有实际内容的可选部分。

README 只表达当前设计，不默认记录修改历史、旧版本、Changelog 或讨论过程。修改时仅更新本次设计变化涉及的内容。

写入完成不代表实现已同步。完成后请用户确认：

> README.md 已完成，请确认是否根据当前设计创建或修改 Skill。

如果当前完成的 README 已有明确的实现确认，直接继续，不重复询问。同一确认不覆盖此后新增的设计变化。

### Step 6：实现完整 Skill

确认 README 已完成且用户授权按当前版本实现，再创建或修改 `SKILL.md` 及设计需要的辅助材料。

将设计转化为执行指令。关键步骤应让执行者知道依据什么信息、采取什么动作或判断、形成什么结果，以及何时进入下一步。仅在影响执行时补充信息不足、检查失败或其他必要分支，不强制每步填写固定表格。

不只复述设计目标。执行所必需的方法应写入 `SKILL.md` 或在相关步骤明确引用随包材料，不能要求执行者依赖未交付的讨论结论。

`SKILL.md` 默认结构：

```markdown
---
name: <skill-name>
description: "说明该 Skill 完成什么任务，以及在什么请求或情境下使用。"
---

# <Skill Name>

## 任务
## 输入
## 原则
## 工作步骤
## 输出
## 校验
```

生成时替换占位符。`name` 与目录名一致，使用 1–64 个小写英文字母、数字或连字符，不能以连字符开头或结尾，也不能含连续连字符；`description` 为 1–1024 字符的非空字符串，同时说明用途和使用时机。不强制其他元数据字段。用户另有目标平台或格式要求时，按已确认的设计实现。

如需要 References，同时创建、修改或删除相关文件，并在具体步骤明确何时读取、如何使用。只修改授权范围内的内容；发现必须改变已确认设计时返回设计讨论，不自行扩展。

### Step 7：校验与交付

先做静态检查：

- 核对用户确认的设计与授权，比较 README 和实现，定位遗漏或矛盾。
- 检查关键方法是否转成具体动作和判断，步骤是否衔接、输出是否明确。
- 检查 YAML 元数据、占位符替换和文件引用；确认 References 有实际用途且在相关步骤按需使用。
- 修改任务对照原文件，检查是否误改无关内容或漏改直接相关位置，删除明显重复和不必要复杂度。

再做必要的场景检查：优先使用用户提供的代表性输入，没有时可构造示例并明确说明。沿关键步骤检查所需信息、判断依据、步骤衔接和输出质量；有重要边界或失败分支时补查，局部修改重点检查变更路径及直接受影响的相邻步骤。

对本 Skill，可按修改范围选择检查以下场景：模糊需求、认可方案但未授权、仅授权 README、确认 README 后续接实现、局部修改、缺少 README、未解释的设计与实现冲突。不要求每轮全部重跑，也不默认新增测试目录或自动评分器。

条件具备且不超出授权时进行真实运行，否则明确只做静态检查或场景推演。推演应指出支持预期行为的规则；真实运行应有实际输出或工具结果。不能把预期行为当作通过证据，也不能把推演表述为运行通过。

在授权范围内修正实现遗漏、格式或引用错误后复查；需要改变已确认设计时先询问用户。仅处于 README 阶段时只检查设计，不为消除待同步差异而提前修改实现。

## 输出

根据当前阶段输出：

- **设计讨论阶段**：任务分析、设计方案和必要的确认问题，不修改文件。
- **README 阶段**：创建或修改后的设计文档，以及实现确认请求；已有有效确认时不重复请求。
- **实现阶段**：完整 Skill，包括 `SKILL.md` 和设计需要的辅助材料。

文件操作后说明实际创建、修改或删除了哪些文件，做了什么检查、结果如何，以及哪些部分尚未验证。修改任务只交付授权范围内的变更。

## 校验

最终确认：

- [ ] 当前阶段和授权范围明确，未重走已完成阶段，也未越权写文件。
- [ ] 任务经过必要拆解，关键问题、质量判断依据和方法足够具体。
- [ ] README 表达当前设计，完成实现后与实际 Skill 一致。
- [ ] 关键方法已落实为可执行动作和判断，不依赖未交付的对话结论。
- [ ] 元数据有效，引用可用，References 有明确用途。
- [ ] 修改未扩大范围，也未增加不必要的复杂度。
- [ ] 必要场景已检查，静态检查、推演和真实运行的范围与结果已如实说明。
